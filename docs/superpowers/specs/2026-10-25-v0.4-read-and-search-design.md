## 1. 意图

v0.3 让本扩展打开的分屏“打开之后”更好用。v0.4 把分屏的入口从“用触发网址搜索”扩大到用户正在看的页面：

- 已经在某个引擎里搜过了（比如直接在 google.com 搜的），点工具栏图标就能把右侧补上，不用重新搜一遍（⑦）。
- 读文章时选中一个词右键，当前页留在左边，右侧出查询结果；再查别的词，右侧原地换（②）。
- 在图片上右键，当前页留在左边，右侧用以图搜图引擎查这张图（⑧）。

代价是加两个权限：`activeTab`、`contextMenus`，都没有安装警告（附录 A 的 F15）。不加 `tabs`，不申请宽泛的 host 权限（用户决定，2026-10-25）。

顺序按路线图 ⑦ → ② → ⑧。三者共用一套记录模型的扩展（3.1），这一步要先做：② 和 ⑧ 的左侧是任意网页，现有代码有两处会把它当成本扩展的搜索页覆盖掉（2.1）。

### 1.1 目标

- **W1 记录模型扩展**：记录能区分“搜索对”（两侧都是本扩展打开的搜索页）和“查询对”（一侧是用户的网页，一侧是本扩展打开的查询结果）。所有会改写标签的路径（go.html、弹窗、快捷键、右键）只改写确认属于本扩展的那一侧。
- **W2 ⑦ 补成分屏**：工具栏弹窗识别出当前标签是某个已配置引擎的结果页时，列出可放在右侧的引擎，点一个就组成分屏（用户决定，2026-10-25：⑦ 放在弹窗里）。
- **W3 ② 边读边查**：选中文字右键，用“查词引擎”在右侧查。查词引擎在设置页单独选，默认跟随默认组合的右侧（用户决定，2026-10-25）。
- **W4 ⑧ 以图搜图**：图片右键，右侧默认用 Google Lens，Bing、Yandex 等可从引擎库添加并切换（用户决定，2026-10-25）。
- **W5 不碰分屏里的页面**：右键时页面已经在任何分屏里（包括本扩展自己的分屏），一律在旁边开一个普通新标签，两侧都不动；只有不在分屏里的页面才成为新分屏的左侧，之后从这个左侧再查，复用它自己的右侧标签（用户决定，2026-10-25）。

### 1.2 非目标（v0.4 不做）

- 弹窗或快捷键里的“互换左右”“拆开分屏”，沿用 Chrome 原生菜单（沿用 v0.3 的用户决定）。
- 右键菜单里展开子菜单、每次现选引擎。查词引擎只在设置页选（用户决定，2026-10-25，选的是“设置页单独选”）。
- 两个以图搜图引擎并排对比（Lens ｜ Bing 一对）。
- 没有公开网址的图片（`data:`、`blob:`）以图搜图。这类图片上不显示菜单项（用户决定，2026-10-25）。
- 上传图片文件、截屏搜图。引擎只拿到图片网址，由引擎服务器自己去下载。
- ⑦ 识别 `%s` 在路径里的模板（如 Google 地图）和改写网址的单页应用（如 Perplexity 结果页没有 `q`）。见 3.2。
- 识别模板 host 以外的地区域名（如 `google.com.hk` 的结果页不会被识别成预置的 Google）（我的决定）。
- 右键菜单项的开关（设置页关掉某一项）。Chrome 没有按扩展隐藏菜单项的入口，需要的话以后再加（我的决定，审阅时请确认 v0.4 不需要）。
- 图片网址带签名参数（`X-Amz-*`、`token`、`sig`）时先弹提示。v0.4 只在设置页和隐私说明里写明风险，提示功能以后再定（我的决定）。
- 按关键词自动选右侧（之后的版本，见路线图）。

### 1.3 反目标（沿用 CLAUDE.md，这一版特别容易碰到的几条）

- 覆盖用户正在读的网页。② ⑧ 的左侧是任意网页，任何“更新对侧”的代码路径都可能把它导航走。只有记录确认是本扩展打开的那一侧才能被改写（用户决定，2026-10-25：没有记录确认的页面一律不覆盖，重启后也不靠猜来复用）。
- 覆盖用户手动建的分屏里的任何一侧（沿用）。
- 申请 `tabs` 或宽泛的 host 权限；为以图搜图引擎申请 host 权限。
- 关键词、选中文字、图片网址发给用户所选引擎以外的任何一方，或进入 `storage.sync`。它们只进 `storage.session`（用户决定，2026-10-25 重申）。
- ② ⑧ 读取或保存页面网址（`pageUrl`、`frameUrl`）。⑦ 只在用户点工具栏图标时经 activeTab 读当前标签网址，用来识别结果页和关键词，不保存网址本身（我的决定：反目标按功能分开写，⑦ 读网址是功能本身）。
- 注入内容脚本；读取页面里除选区和被右键图片网址以外的任何内容。
- 改动 Chrome 原生右键菜单项（“用 Google 搜索”“用 Google 搜索图片”）或它们的行为。

### 2.1 现有代码里必须改的地方（W1）

不改的话，查询对的左侧网页会被导航走：

1. **go.html 在查询对的查询一侧运行。** 用户在右侧窗格的地址栏发起搜索，go.html 在右侧标签里跑，判定为 `own` 后走 `reuse`，`refreshPair` 先 `tabs.update(peer)`（`src/chrome/split-actions.js` 的 `refreshPair`）。这时 peer 就是用户的网页。
2. **换右侧按标签顺序选目标。** `ownedPair`（`src/chrome/right-switch.js`）按 index 定左右。用户用原生“互换位置”之后，网页排到了右边，弹窗的“换右侧”和快捷键 `cycle-right` 会把网页导航走。
3. **记录读写会丢掉新字段。** `parseRecord`（`src/lib/split-owner.js`）只返回 `{peer, splitViewId, mode, engine, query}` 五个字段；`writeEngine` 在解析结果上展开写回，`makeRecords`、`writePair`、`refreshPair`、`recordNewPair` 都没有 `role`、`input` 参数。弹窗或快捷键在查询对上换一次右侧，`lookup` 记录就丢了 `role`，按“没有 role 按 search 解析”变成 `search`，和对侧的 `page` 配不上，整对判 `stale`，功能静默失效。改法见 3.1“记录读写函数”。
4. **兜底判定会覆盖没有记录的网页。** `decideSplit` 在分屏中对 `fallback-own` 也走 `reuse`。浏览器重启或扩展更新后 `storage.session` 清空，Chrome 恢复的查询对两侧都没有记录；go.html 在查询一侧运行时，对侧是用户的网页，只要它“像某个文字引擎的搜索页”（本身是 Google 结果页，或配置了路径模板引擎、网页恰好是 Wikipedia 词条），就会被覆盖。改法见 3.1“兜底”。

`inspectTab`、`tabs.onRemoved` → `clearPair`、`markStale`、`staleMarker` 的判定逻辑与角色无关，不用改；它们读写的记录形状随 `parseRecord` 一起扩展（`staleMarker` 是展开原记录，`role`、`input` 会原样保留）。

## 3. 设计

### 3.1 记录与归属模型（三个功能共用）

**记录形状**（我的决定）：键仍是 `split:<tabId>`，值在 v0.3 的基础上加两个字段：

```
{ peer, splitViewId, mode: "split" | "adjacent",
  role: "search" | "page" | "lookup",
  input: "text" | "image",      // 只有 role 为 page、lookup 时才有
  engine, query }
```

- `role`：
  - `search`：本扩展打开的搜索页。go.html 和 ⑦ 建的一对，两侧都是 `search`。
  - `page`：用户的任意网页，即 ② ⑧ 查询对的左侧。`engine` 为空字符串。
  - `lookup`：本扩展打开的查询结果，即查询对的右侧。`engine` 是查词引擎或以图搜图引擎的 id。
- `input`：查询对的输入类型，两侧记录写同一个值。同一个网页先查词、再查图，用的是同一个右侧标签，`input` 跟着改（3.3 第 4 行）。
- `query`：`search` 对是关键词；`text` 查询对是规范化后的选中文字（3.3）；`image` 查询对是图片网址。两侧记录写同一个值，弹窗在哪一侧打开都能显示。
- **没有 `role` 的记录按 `search` 解析**（我的决定）。`storage.session` 在扩展更新时会清空（F23），线上不会遇到 v0.3 形状的记录；保留这条兼容只是让测试和 e2e 里手工构造的旧形状照常可用。`role` 是别的值、`role` 为 `page`/`lookup` 却没有合法的 `input`、`engine` 为空却不是 `page`，一律当作没有记录。
- 记录只在 `storage.session`，不进 `storage.sync`，不外发（沿用）。

**记录读写函数**（2.1 第 3 条的改法，我的决定）：

- `parseRecord`：多解析、多校验 `role` 和 `input`，按上面的规则返回完整形状（没有 `role` 时补成 `role:"search"`，不带 `input`）。
- `makeRecords`、`writePair`：两侧各收一个 `role`（`roleA`、`roleB`），再收一个共用的 `input`（`search` 对不传）。
- `writeEngine`：仍在解析结果上展开写回；`parseRecord` 保留了新字段，它不用改，但要有测试。
- `refreshPair`（go.html 的 `reuse`/`join`）：写回时两侧都是 `role:"search"`，不带 `input`（go.html 在 `page` 一侧复用时整对改写成搜索对，见下表）。
- `recordNewPair`、`openRight`：多收 `role`、`input`，go.html 和 ⑦ 传 `search`，② ⑧ 传 `page`/`lookup`。
- 新增 `writeLookup`（或给 `writePair` 加参数，由实现者定）：② ⑧ 第 3、5、6 行整对改写 `engine`、`query`、`input`，`role` 不变。
- 必加的测试：`writeEngine` 之后 `role`、`input` 不变；`staleMarker` 之后 `role`、`input` 不变；`role:"lookup"` 缺 `input` 时 `parseRecord` 返回 null；`refreshPair` 在 `page` 一侧运行后两条记录都是 `search`。

**归属判定**（`src/lib/split-owner.js` 的 `judgeOwnership`）：v0.3 的规则不变，`recordMatches` 多核对两条，任一不满足判 `stale`（我的决定）：

1. 两侧的 `role` 能配对：`search` 配 `search`，或 `page` 配 `lookup`。
2. 查询对两侧的 `input` 相同。

**兜底**（2.1 第 4 条的改法；用户决定，2026-10-25：重启或更新后记录清空时一律不复用，在旁边新开一对）：

- `judgeOwnership` 的兜底判定本身不改，仍可能判出 `fallback-own`（只拿**文字**引擎的模板比对，以图搜图引擎不参与），日志和测试照常能看到这个结论。
- **`fallback-own` 不再允许任何调用方改写标签。** `decideSplit` 把 `fallback-own` 当作 `foreign`：在该分屏右边新建一对，原分屏两侧都不动。弹窗、快捷键、右键本来就只认确切的 `own`。
- 代价：浏览器重启或扩展更新后（记录清空），在 Chrome 恢复出来的本扩展分屏里再触发一次，会在旁边多开一对，而不是原地复用；之后新开的这一对有记录，照常复用。v0.3 的兜底复用因此取消，CLAUDE.md 机制速览里“只有两侧都没有记录才走兜底”那句跟着改（3.9）。用户在“两侧都像搜索页才复用”“一律不复用”“照 v0.3 不变”三者中选了一律不复用。
- 不再需要的东西不删：`judgeOwnership` 的 `engines` 参数、`looksLikeSearchPage` 保留（⑦ 的 `result-match.js` 复用后者的思路），只是不再导向覆盖。
- Chrome 重启后会不会恢复拆分视图没实测（S14）。不恢复的话这条风险本来就不存在，上面的改法仍然保留，作为扩展更新、重新加载后的保险。

**谁能改写哪一侧**（W1 的核心规则，我的决定）：

| 调用方 | 当前标签的记录 | 允许改写 |
|---|---|---|
| go.html | `search`（own） | 对侧（沿用 `reuse`/`join`） |
| go.html | `page`（own） | 对侧（查询结果）。当前标签已经被用户的搜索导航走了，整对改写成 `search` 对 |
| go.html | `lookup`（own） | 不改写对侧。当成“不是本扩展的”：在分屏中走 `foreign`，在相邻对中走 `new` |
| go.html | 两侧都没有记录（`fallback-own`） | 不改写任何一侧，走 `foreign`（见“兜底”） |
| 弹窗换右侧、快捷键 | `search` 对 | 看得见的右侧（index 大的一侧，沿用 v0.3） |
| 弹窗换右侧、快捷键 | 查询对 | 永远是 `role` 为 `lookup` 的那一侧，与标签顺序无关 |
| 右键 | 见 3.3 判定表 | 只有当前标签是查询对的 `page` 一侧时，才改写它的 `lookup` 一侧 |

- go.html 的改动落在 `decideSplit`：多收一个 `role` 输入，`role` 为 `lookup` 时把 `own` 当成不是本扩展的；`fallback-own` 一律当成 `foreign`（见上文“兜底”）。纯函数，带 node 测试。
- go.html 在 `page` 一侧走 `reuse`/`join` 时，`refreshPair` 按标签顺序决定哪一侧放左侧引擎，这和 v0.3 一样；两侧此时都已经是本扩展的搜索页或用户主动离开的页面，不涉及覆盖。
- go.html 在 `lookup` 一侧走 `new`（相邻对、窗口不在分屏中）时，当前标签成为新搜索对的左侧，原来的 `page` 标签的记录会指向一个已经换了对象的标签，下次读到时判 `stale` 并改写成永久失效标记（v0.3 的 `markStale`）。方向是安全的：这个网页不会再被当成本扩展的。

**`ownedPair`（`src/chrome/right-switch.js`）**：返回值加 `kind`（`"search"` 或 `"text"`/`"image"`）。查询对时，`right` 固定是 `lookup` 一侧，`left` 是 `page` 一侧（我的决定）。`switchRight` 只动 `pair.right`，所以弹窗和快捷键自动满足上表。`switchRight` 写回记录时 `role`、`input` 不变（见“记录读写函数”）。

**按 `kind` 取引擎**（我的决定）：现在弹窗的 `onSwitch` 在 `cfg.engines` 里找引擎，`popupView` 的 `find` 查 `engines` 和 `hidden`，`cycleRight` 把 `engines` 传给 `nextRightEngine`，三处都只看文字引擎，图片查询对的右侧会显示成“已删除的引擎”、也换不成。改法：

- `mergeConfig` 多输出 `imageEngines`（已合并内置 `lens`，在前）和解析后的 `imageEngine`、`lookupEngine` id（见 3.5）。
- 新纯函数 `enginesFor(cfg, kind)`：`image` 返回 `cfg.imageEngines`，其余返回 `cfg.engines`；`engineById(cfg, kind, id)` 在对应列表（文字时含 `hidden`）里查。放在 `src/lib/engines.js` 或 `image-engines.js`，由实现者定。
- 弹窗的候选和查找、`onSwitch`、快捷键都改走这两个函数。

**快捷键 `cycle-right`**：`nextRightEngine` 按 `kind` 取候选（我的决定）：

- `search` 对和 `text` 查询对：文字引擎，按显示顺序，跳过 `cycleExclude`（沿用）。
- `image` 查询对：以图搜图引擎，按列表顺序，不看 `cycleExclude`。以图搜图引擎行上没有“参与快捷键轮换”开关（3.5）。

**清理**：`tabs.onRemoved` → `clearPair`、读到失效记录时的顺手清理，规则不变（v0.3 3.1）。

**SW 里的串行**（我的决定）：两次右键几乎同时触发时，两个 `onClicked` 都读到“无记录”、都去 `createPaired`，第二次 `splitWithTabId` 报 `already in a split view`，退回成普通标签，留下一个孤立标签；⑦ 和右键同时操作同一个标签也一样。所以 SW 里 ② ⑧ 的 `onClicked` 和 ⑦ 的 `complete-split` 共用一条串行链，每次在链上**重新判定**（重新 `tabs.get`、`inspectTab`）再执行。用一条全局链，不按 `tabId` 分锁：操作都是用户点击触发的，排队等的时间可以忽略，全局链更简单、也覆盖了两个标签互为对侧的情况。go.html、弹窗在各自的页面里运行，和 SW 之间仍可能交错，最坏结果同 v0.3（记录被删或判失效，之后新开一对），方向安全。

### 3.2 ⑦ 把现有搜索补成分屏（工具栏弹窗）

**用户流程**

1. 用户在某个已配置引擎的结果页上（直接在 google.com 搜的，或者 G5 降级后留下的单页搜索），点工具栏图标。
2. 弹窗显示“补成分屏”区：一行“识别到 Google 搜索：<关键词>”，下面是可放在右侧的引擎按钮。
3. 点一个引擎：当前页留在左边不动，右侧打开同一关键词的搜索，组成分屏。窄窗口时右侧开在紧邻的后台标签。
4. 之后这一对就是本扩展的搜索对，弹窗换右侧、快捷键、go.html 复用、关标签清理都照常生效。

**弹窗按当前标签的状态显示什么**（我的决定）：

| 当前标签的状态 | 弹窗显示 |
|---|---|
| 属于本扩展的一对（`own`，任意 `role`） | v0.3 的对视图（查询对的显示见 3.3） |
| 在任何分屏中，但不是 `own` | v0.3 的“不是 Split Search 打开的拆分视图”说明 |
| 窗口不是 `normal` | 同上 |
| 不在分屏中（`none` 或 `stale`），网址识别成结果页，关键词非空 | “补成分屏”区，加“打开设置页” |
| 读不到网址、识别不出、关键词为空 | v0.3 的说明 |

- `stale` 也允许补：v0.3 的 go.html 对不在分屏中的 `stale` 标签同样走 `new`。补成之后新写的记录覆盖当前标签的旧记录，对侧旧记录按 v0.3 规则失效。
- 不在分屏中、但属于本扩展相邻对的标签，判 `own`，显示对视图，不显示“补成分屏”。

**识别结果页**：新纯函数文件 `src/lib/result-match.js`（带 node 测试），输入当前网址和文字引擎列表，输出识别到的引擎、关键词和建议的右侧引擎。规则（我的决定）：

1. 先试一次 `parseTrigger`。成功说明这可能是 G5 降级留下的触发网址，但 `parseTrigger` 只看 `_ss` 和左侧引擎的 `leftParam` 在不在，不核对网址的 origin 和路径（`https://任意站/?q=x&_ss=google,bing` 也会被它认成 Google 搜索）。所以还要拿 `_ss` 里的左侧引擎套第 2 步的三条检查（origin、`pathname`、固定参数），都通过才算识别成功，引擎和关键词取自它，建议的右侧取 `_ss` 里的右侧 id；不通过就当作识别不出，**不再**往下走第 2 步（我的决定：带 `_ss` 的网址只按 `_ss` 声明的引擎识别，避免一个网址被认成两个引擎）。
2. 否则逐个比对能作左侧的模板（`validateTemplate(...).leftParam` 不为空）：
   - origin 与模板完全相同，`pathname` 与模板相同（同 `looksLikeSearchPage` 的查询模板分支）。
   - 模板里除 `%s` 以外的固定参数，在网址里都存在且值相同（GitHub 的 `type=repositories`、Wikipedia 的 `title=Special:Search`）。网址多出来的参数不影响。
   - `URLSearchParams.get(leftParam)` 去掉首尾空白后非空。
3. 同时匹配多个时，依次按“固定参数多的优先 → 模板 `pathname` 长的优先 → 显示顺序靠前的优先”挑一个。
4. 建议的右侧：有 `_ss` 时取它；否则取默认组合的右侧；默认组合的右侧恰好就是识别出的引擎时，改取默认组合的左侧。

不支持的模板：

| 模板类型 | v0.4 |
|---|---|
| `%s` 在查询参数里（Google、Bing、DDG、Kagi、YouTube `search_query` 等） | 支持 |
| 带固定参数（GitHub、Google Translate、Wikipedia） | 支持，固定参数必须一致 |
| `%s` 在路径里（Google 地图、模拟引擎 C 的 `/wiki/%s`） | 不支持。EscapePath 不转义 `/`，无法唯一还原关键词 |
| `%s` 只是参数值的一部分（Stack Overflow (Google) 的 `q=%s+site%3A…`） | 不支持（`leftParam` 为空） |
| 单页应用改写网址（Perplexity 结果页没有 `q`） | 不支持 |

**引擎按钮**：显示顺序里除识别出的引擎以外的全部文字引擎，建议的右侧排第一并高亮（我的决定）。不看 `cycleExclude`（每次都是用户亲手点选，同 v0.3 弹窗）。以图搜图引擎不出现。

**执行放在 SW**（我的决定）：

- 理由：新标签进分屏时窗口焦点和内容区会变，弹窗可能被关掉，弹窗里的 JS 中途被杀就会留下没写记录的分屏（备忘第 4 节第 1 条）。放进 SW 后，这个问题不需要 spike 也能绕开。activeTab 授予的是扩展对这个标签的权限，按源码推断 SW 同样能读到网址（F5），由 S2 实测确认（见下文“SW 执行”）。
- 消息：弹窗经 `runtime.sendMessage` 发 `{ type: "complete-split", tabId, engineId }`，只带标签 id 和用户点的引擎 id。**不带网址和关键词**，SW 不信任弹窗算出来的结果。
- SW 校验（`runtime.onMessage`，顶层同步注册）：
  - `sender.id === chrome.runtime.id`，并且 `sender.url` 是本扩展的 `popup/popup.html`（带不带 `?tabId=` 都算，e2e 用这个接缝）。不注册 `onMessageExternal`，manifest 也没有 `externally_connectable`，网页发不进来。
  - `type` 认识，`tabId` 是非负整数，`engineId` 是现有未隐藏文字引擎的 id。
  - 不满足就回 `{ ok: false, code }`，什么都不做。
- 回复写法（我的决定）：监听器 `return true`，用 `sendResponse` 异步回复，不依赖“监听器返回 Promise”在 155/156 上的支持情况。
- SW 执行（在 3.1 的串行链上）：`tabs.get(tabId)` 重新读标签和网址 → 重新识别 → `engineId` 等于识别出的引擎时回 `message_rejected`（弹窗按钮本来就排除了它，我的决定）→ `windows.get` 读窗口类型和宽度 → `inspectTab` 重新判定 → 条件仍满足才建。任何一步不满足，回对应错误码（3.8）。
- SW 能读到 activeTab 授予的网址：activeTab 授予的是扩展对这个标签的权限，不区分扩展里的哪个页面，源码推断 SW 同样读得到；S2 一并实测“真点图标后 SW 里 `tabs.get(tabId).url` 有值”。不成立时 ⑦ 改在弹窗里执行，S1 随之变成必须先做（我的决定）。
- 建法：复用 `createPaired`（窄窗口时 `split:false`，新标签 `active:false`）和 v0.3 的复核（`confirmedSplitViewId`）。真的建成分屏才写 `split` 记录；窄窗口写 `adjacent` 记录；想分屏却退化成普通标签时不写记录（沿用 v0.3）。记录两侧都是 `role:"search"`，左侧 `engine` 是识别出的引擎，右侧是用户点的引擎，`query` 是识别出的关键词。
- **当前标签不导航**。左侧页面原样保留，包括它网址里可能带着的 `_ss`（我的决定：接受，验收表写成预期行为）。之后用户刷新左侧时，如果这个引擎已经授权，DNR 会把它重定向到 go.html，导航类型是 reload，页面只显示“重新执行”按钮；没授权（多半正是当初 G5 降级的原因）时刷新就是普通刷新。为此改写成去掉 `_ss` 的网址会重载页面，和“当前页不动”冲突，所以不做。
- ⑦ 建成后左侧记成 `role:"search"`，之后 go.html 在右侧窗格发起搜索时 `reuse` 会改写左侧；用户在左侧点进别的网站以后也一样。这与 v0.3 搜索对的已知限制相同：左侧是本扩展识别过的搜索结果页，记录也确认了这一点（我的决定：接受）。
- 回复 `{ ok: true, mode: "split" | "adjacent" | "plain" }`。弹窗如果还开着，按回复刷新：建成了就换成对视图；`adjacent` 显示一句“窗口较窄，右侧在旁边的标签打开”；`plain`（退化）显示“没能组成拆分视图，已在旁边的标签打开”（我的决定）。

**权限使用**：activeTab 只用来读当前标签的 `url`。建分屏不需要权限（F7）。左侧引擎授过权时网址本来就读得到；activeTab 补上的是“只作右侧、没授权的引擎”和“没给左侧引擎授权”两种情况。

**窄窗口与非 normal 窗口**：窄窗口按 v0.3 3.3 的阈值和开关，右侧开成后台相邻标签（我的决定：与 go.html 一致，不激活；弹窗那句提示足够）。窗口不是 `normal` 时不显示“补成分屏”，不在别的窗口里新建（我的决定）。原因：⑦ 的价值在于保留当前页，搬到别的窗口就没有意义了。

### 3.3 ② 边读边查（选中文字右键）

**用户流程**

1. 在 http(s) 网页上选中文字，右键选“在拆分视图中用 Bing 搜索“…””（标题见 3.13，引擎名是当前的查词引擎）。
2. 当前页留在左边，右侧打开查词引擎的结果，组成分屏。
3. 在同一页上再选别的词右键：右侧原地换成新结果，不多开标签。
4. 页面已经在任何分屏里时，结果在旁边的普通新标签打开，分屏两侧都不动（用户决定，2026-10-25）。

**输入处理**（我的决定）：

- `selectionText`：去掉首尾空白，把所有连续空白（含换行、制表符、不间断空格）合并成一个空格，再截到上限（不切断代理对）。结果为空就不处理。上限取 500 个码点和 S3 实测的 Chrome 自己的截断值中较小的一个（我的决定）。菜单标题另由 Chrome 截到 75 字符（F10），与这个上限无关。
- `info.editable === true`（选区在输入框、文本域或可编辑区域里）时不处理，只记日志（我的决定）：菜单项在这里可能照样出现（`selection` 在可编辑区域里有选区时也可能匹配，待 S6 实测），但用户正在输入的内容不发出去。S6 若测出 Chrome 在可编辑区域里根本不显示本扩展的菜单项，这条只作保险。验收表写成预期行为。
- 不读 `pageUrl`、`frameUrl`，不存，不发（我的决定）。判定只用 `tab` 的 `id`、`index`、`windowId`、`splitViewId`，这几个字段不需要任何权限。
- 右键路径调用 `inspectTab` 时传空的引擎列表（`engines = []`，我的决定）。这样兜底不会去比对对侧网址；`peerOf` 仍会顺带拿到 `tabs.query` 返回的对侧 `url`（有 host 权限时），但右键路径不使用它。判定结果不变：没有记录的分屏本来就落到第 4 行。
- 点菜单项顺带授予的 activeTab（F3）② 不用。

**判定表**：新纯函数文件 `src/lib/lookup-decision.js`（带 node 测试），② 和 ⑧ 共用。被点击的标签记作 T，T 的归属由 `inspectTab` 给出：

| # | T 的状态 | 动作 | 记录 |
|---|---|---|---|
| 1 | `tab` 缺失、`tab.id < 0`，或输入无效 | 什么都不做，只记日志 | 不动 |
| 2 | T 的窗口不是 `normal` | 在最后聚焦的 normal 窗口开一个普通标签（`active:true`）并聚焦该窗口；没有 normal 窗口就新建一个 | 不写 |
| 3 | T 在分屏中，判 `own`，T 是查询对的 `page` 一侧 | 就地更新 `lookup` 一侧（`tabs.update`），不激活（它就在分屏里，看得见） | 整对改写：新 `engine`、`query`、`input`，`splitViewId` 沿用 |
| 4 | T 在分屏中，其他一切情况：本扩展搜索对的任一侧、查询对的 `lookup` 一侧、用户分屏、`fallback-own`、`stale` | 在分屏右边（两侧最大 index + 1）开一个普通标签，`active:true` | 不写 |
| 5 | T 不在分屏中，判 `own`，T 是相邻查询对的 `page` 一侧，窗口仍窄 | 更新 `lookup` 标签并激活它 | 改写 `adjacent` |
| 6 | 同 5，但窗口已经不窄或关掉了降级开关 | 更新 `lookup` 标签，再 `createSplit([T, lookup])` 拼成分屏（同 v0.3 的 `join`），复核后改写 `split`；拼不成退回第 5 行 | 同 v0.3 `join` |
| 7 | T 不在分屏中，判 `own`，T 是相邻查询对的 `lookup` 一侧 | 在这一对的右边（两者较大 index + 1）开一个普通标签，`active:true` | 不写 |
| 8 | T 不在分屏中，其他情况（无记录、`stale`、本扩展相邻搜索对的任一侧） | `createPaired`：宽窗口组成分屏，新标签 `active:false`；窄窗口开相邻标签，`active:true` | 建成分屏写 `split`，窄窗口写 `adjacent`，`page`↔`lookup`；想分屏却退化成普通标签时不写 |

说明：

- 第 3、4 行是用户决定 2 的直接落实：分屏里只有“自己是网页、对侧是本扩展查询结果”这一种情况会复用，其余一律开普通标签。
- **第 4 行包括查询对的 `lookup` 一侧。** 用户在右侧结果里再选词右键，结果开在新标签里，不原地改写右侧（按用户决定 2 的字面执行：“已在任何分屏里，包括本扩展的分屏，一律开新标签”）。摸排备忘曾建议这种情况原地更新右侧，这里没有采用。审阅时请确认。
- 第 7 行与第 4 行保持一致（我的决定）：查询结果标签不会变成新查询对的网页一侧。
- 第 8 行里“本扩展相邻搜索对的一侧”：T 的旧记录被新查询对覆盖，原对侧下次读到时判 `stale`、改写成永久失效标记。这不会覆盖任何页面。同样是本扩展的搜索对，在分屏中走第 4 行（开普通标签），相邻时走第 8 行（T 成为新分屏的左侧），理由是用户决定 2 只管“已在分屏中”的页面：相邻对没有在分屏里，T 照常可以成为新分屏的左侧，原来那一对随之失效（我的决定：保持现状，验收表写明）。
- 普通标签的位置：第 4 行沿用 `openForeign` 的算法（分屏两侧最大 index + 1），第 7 行是这一对两个标签的较大 index + 1（我的决定：用户把别的网页拖到查询标签右边时，`T.index + 1` 会插进这一对中间，用较大 index 避开）。固定标签和标签组的继承由 Chrome 处理（已知事实）。
- `tab` 缺失（例如在侧边栏里右键）时，第 1 行只记日志，用户点了菜单看不到任何反应（我的决定：接受，`documentUrlPatterns` 只放行 http(s)，这种情况很少；验收表写成预期行为）。
- 选区在 iframe 里：`documentUrlPatterns` 按选区所在 frame 的网址匹配（待 S6 确认），所以 `srcdoc`、`about:blank`、沙箱 iframe 里的选区不显示菜单项，跨 origin 的 http(s) iframe 里显示；`tab` 仍是顶层标签，判定照常（我的决定：接受，S6 实测后写进已知事实）。
- 弹窗换右侧之后，下一次右键（第 3 行）仍按设置页的查词引擎查，会把右侧换回去（我的决定：保持按设置页走，和菜单标题里写的引擎名一致；验收表写明，避免被当成 bug）。
- 普通标签用 `active:true`（我的决定）：用户刚点了菜单，应该马上看到结果。
- **窄窗口里查询标签用 `active:true`**（我的决定，和 go.html、⑦ 的后台标签不同）。go.html 的左侧就是当前标签，用户看得到结果；② 的左侧是用户原来的页面，右侧放后台的话，点了菜单什么都看不到。复用时（第 5 行）同样激活。
- 第 3、5 行 `tabs.update` 抛错（查询标签刚被关掉）：退回第 8 行的新建（我的决定）。
- 第 3 行可能把用户在右侧点进的别的网站覆盖掉。这与 v0.3 弹窗换右侧的已知限制相同（v0.3 3.4），右侧本来就是本扩展打开的，接受。

**查询网址**：`expandTemplate(查词引擎.url, 规范化后的文字)`，与 go.html 展开右侧时相同。只发给查词引擎。

**查词引擎**：见 3.5。

### 3.4 ⑧ 以图搜图

**用户流程**

1. 在网页图片上右键，选“在拆分视图中用 Google Lens 搜索图片”（引擎名是当前的以图搜图引擎）。
2. 当前页留在左边，右侧打开以图搜图引擎，引擎服务器自己下载这张图。
3. 同一页再查别的图（或者再查词）：复用同一个右侧标签。

**菜单项**：`contexts: ["image"]`，`targetUrlPatterns: ["https://*/*", "http://*/*"]`，用来在 `data:`、`blob:` 图片上不显示（用户决定，2026-10-25）。这个过滤的实效要 S7 确认，见第 4 节；确认之前处理函数自己也再查一遍：`info.mediaType === "image"`，`srcUrl` 能解析且协议是 `http:` 或 `https:`，不满足按判定表第 1 行处理（我的决定）。

**判定和布局**：与 ② 相同的判定表（3.3），`input:"image"`，`query` 存图片网址。同一个网页的 `lookup` 标签在查词和查图之间共用（第 3 行整对改写时 `input` 跟着变）（我的决定）。理由：一个网页只配一个右侧，标签不会越开越多。

**查询网址**：`expandTemplate(以图搜图引擎.url, srcUrl)`，即模板里的 `%s` 换成 `encodeURIComponent(srcUrl)`。

**权限使用**：只要 `contextMenus`。`srcUrl` 来自 `OnClickData`，不需要 host 权限或 activeTab。

**限制**（设置页写明，见 3.11）：

- 没有公开网址的图片（页面内嵌、临时生成）不显示菜单项。
- 要登录、要 cookie、限 Referer 才能看的图片，引擎下载不到。扩展事先检测不出来（跨 origin 读状态码需要那个 origin 的 host 权限），引擎会显示空结果，Bing 还会悄悄跳回首页（F22）。
- 图片网址可能本身就是访问凭证（带签名、有效期的 CDN 地址），发给引擎等于交出访问权限。
- Lens 落地页会按地区换域名，右侧靠记录和 `splitViewId` 识别，不受影响。

### 3.5 引擎配置：查词引擎与以图搜图引擎

**查词引擎**（用户决定，2026-10-25：设置页单独选，默认跟随默认组合的右侧）：

- `storage.sync` 新增顶层键 `lookupEngine`：字符串，文字引擎的 id。没有这个键，表示“跟随默认组合的右侧”（我的决定：不写默认值进存储，这样用户改默认组合时查词引擎自动跟着变）。
- `mergeConfig` 解析出实际使用的 id：键存在且对应一个未隐藏的文字引擎就用它，否则用 `defaultPair[1]`。
- 可选范围：全部未隐藏的文字引擎，包括只能作右侧的（路径模板、`leftDiscouraged`）。
- 删除或隐藏的正好是查词引擎时，`edits.js` 一并删掉 `lookupEngine` 键，回到“跟随”（我的决定，做法同 `cycleExclude`）。即使没删掉，解析时也会退回默认组合的右侧。

**以图搜图引擎**（我的决定：单独一套列表，不和文字引擎混在一起）：

- 理由：
  - 两套引擎基本不重合，编码对象也不同（整个图片网址）。
  - 文字引擎会流进 DNR 的 `leftHosts`、默认组合、触发网址生成器、弹窗候选、快捷键轮换、兜底判定。混在一起要在每处加过滤，漏一处就可能把以图搜图引擎写进 DNR 规则。分开之后这些地方一行都不用改。
  - 以图搜图引擎不经过 DNR，不需要授权，设置页不显示授权按钮。
- 内置一个：`lens`，Google Lens，`https://lens.google.com/uploadbyurl?url=%s`，写在代码里（`src/lib/image-engines.js`，纯逻辑），不能删除（用户决定，2026-10-25：默认 Google Lens）。
- `storage.sync` 新增两个顶层键：
  - `imageEngines`：自定义以图搜图引擎数组，项是 `{ id, name, url }`，`mergeConfig` 主动清洗，只认这三个字段。
  - `imageEngine`：选中的以图搜图引擎 id。没有这个键或 id 找不到时用 `lens`。
- **id 与文字引擎共用一个命名空间**（我的决定）：都要符合 `ID_PATTERN`，`isIdTaken` 同时查两套列表（文字引擎预置、自定义文字引擎、`lens`、自定义以图搜图引擎）。从文字引擎库和以图搜图引擎库添加时，`uniqueId` 的 `taken` 都用这个查两套的 `isIdTaken`，所以用户已有一个叫 `bing-img` 的自定义文字引擎时，从以图搜图引擎库添加 Bing 会得到 `bing-img-2`。测试覆盖两个方向的冲突。记录里的 `engine` 因此不会有歧义。
- `mergeConfig` 的输出多三项：`imageEngines`（`lens` 在前，后接清洗过的自定义项）、`imageEngine`（解析后的 id）、`lookupEngine`（解析后的 id）。调用方按 3.1 的 `enginesFor`/`engineById` 取引擎（我的决定）。
- 模板校验复用 `validateTemplate`（要有 `%s`、http(s)、精确 host、不能带 `_ss`）。`leftParam` 对以图搜图引擎没有意义，不看。
- 引擎库：`src/lib/image-engines.js` 里另放一个以图搜图引擎库，v0.4 收录 Bing Visual Search（`bing-img`）、Yandex Images（`yandex-img`）、TinEye（`tineye`）、SauceNAO（`saucenao`）；后两个经 S8 由用户用住宅 IP 验证（2026-10-25），百度识图、搜狗不收（我的决定，理由见附录 B）。收录规则沿用 v0.3：先在真机点一遍。
- 设置页能做的：从引擎库添加、手动新增（名称 + 模板）、删除自定义项、选默认。不做改名、编辑、排序（我的决定）：要改就删了重加，列表很短。
- 存储上限：`imageEngines` 同样受 8192 字节单项上限约束，写前预检，超限显示现有的 `config_too_large`。

### 3.6 右键菜单注册与 SW 里的文案

**两个菜单项**（我的决定）：

| id | contexts | documentUrlPatterns | targetUrlPatterns | 标题 |
|---|---|---|---|---|
| `ss-lookup-text` | `selection` | `https://*/*`、`http://*/*` | — | `menu_lookup_text`，带查词引擎名和 `%s` |
| `ss-lookup-image` | `image` | `https://*/*`、`http://*/*` | `https://*/*`、`http://*/*` | `menu_lookup_image`，带以图搜图引擎名 |

- 不加 `editable`。可编辑区域里有选区时菜单项会不会照样出现，待 S6 实测；处理函数对 `info.editable === true` 一律不处理（3.3）。
- 标题里的引擎名是用户数据（我的决定）：插入前把 `&` 写成 `&&`（防止被当成助记键），把引擎名里的 `%s` 改成 `% s`（防止 Chrome 把它换成选中的文字）。这一步写成 `src/lib/` 里的纯函数，带测试；`&&` 是否显示成单个 `&` 由 S11 确认。
- 两项同时适用时（选区里有图片），Chrome 会把它们收进一个以扩展名命名的子菜单，这是 Chrome 的固定行为，接受。
- 无痕窗口里不出现（`incognito: "not_allowed"`，备忘推断，S6 确认）。

**注册时机**（F13）：

- `runtime.onInstalled`（安装、重新加载、更新）和 `runtime.onStartup`：先 `removeAll`，再 `create` 两项（我的决定）。`onStartup` 也重建一次，是为了在浏览器界面语言变化后（`uiLocale` 为 `auto` 时）刷新标题。
- `storage.onChanged`（`sync`）里**任何**变化都完整重建一次（`removeAll` + `create`），不用 `contextMenus.update`，也不维护“哪些键影响标题”的清单（我的决定）。理由：`update` 在上一次 create 失败或和 `removeAll` 交错时会报 `Cannot find menu item`，完整重建没有这个问题；标题依赖的键（`uiLocale`、`lookupEngine`、`defaultPair`、`imageEngine`、`imageEngines`、`customEngines`、`presetOverrides`）以后再变也不会漏。设置页的写入频率很低，重建两项菜单的开销可以忽略。
- 重建挂在 `menus.js` 自己的一条串行链上（和 DNR 重建那条链分开，互不阻塞），后一次一定读到最新配置。链上每一步先 `await` 惰性初始化的 `ready`（见下文“SW 里的界面文案”），再 `loadConfig`、`setLocale`、`removeAll`、`create`；任何一步失败只记日志，链不断。
- 必加的测试：隐藏查词引擎以后，标题退回默认组合右侧的引擎名；改 `uiLocale` 后标题换语言。
- 处理函数在 SW 顶层同步注册（MV3 要求）。`onClicked` 本身不用 `t()`，不必等 `ready`。

**SW 里的界面文案**（我的决定，选备忘 3.3 的第一种办法）：

- 让 `src/chrome/i18n.js` 能在 SW 里用：`setLocale` 里写 `document.documentElement.lang` 的那一行加 `typeof document` 守卫；SW 只用 `initI18n`、`setLocale`、`t`，不用 `applyI18n`。
- 模块 SW 不能用顶层 `await`，而 `t()` 在目录没加载完时会抛错。`menus.js` 里放一个惰性的 `ready`：第一次用到时才调用 `initI18n()` 并缓存这个 Promise，失败时清掉缓存、下次重试（我的决定）。每次重建前按 `storage.sync` 的 `uiLocale` 调一次 `setLocale`，标题跟随设置页选的语言。
- 读的是包内 `_locales`，仍是唯一允许的 `fetch`，不用改硬约束。
- 不为菜单标题开 `chrome.i18n.getMessage` 的例外：那样标题就不跟随设置页选的语言，和其余界面不一致。

### 3.7 窄窗口与非 normal 窗口（汇总）

| 入口 | 窄窗口（`width < 960` 且 `narrowFallback` 不为 false） | 窗口不是 normal |
|---|---|---|
| go.html | 沿用 v0.3 | 沿用 v0.3（在 normal 窗口新建一对） |
| ⑦ 弹窗 | 右侧开在相邻后台标签，记 `adjacent` | 不显示“补成分屏” |
| ② ⑧ 右键 | 查询标签开在相邻位置并激活，记 `adjacent`；复用时激活 | 在最后聚焦的 normal 窗口开普通标签，不写记录 |

- 判断窗口类型一律用 `windows.get(tab.windowId).type === "normal"`，不是 normal 就绝不调用分屏 API（已知事实：popup/app 窗口里调用可能 CHECK 崩溃）。
- Document PiP 窗口（F17）：S5 要确认它的 `type` 是什么、PiP 里右键时 `onClicked` 的 `tab` 是哪个标签。如果 PiP 报的是 `normal` 并且 `tab` 指向 PiP 自己，就要加一道额外的拦截（设计分支见第 4 节）。
  - **S5 实测（2026-10-25，Chrome 156，Linux）**：PiP 报 `type:"normal"`、`alwaysOnTop:true`，自带一个标签，`getLastFocused({windowTypes:["normal"]})` 会返回它；按 `createPaired` 的参数在它上面调分屏 API，Chrome 156 直接崩溃；“核对 `tabs.query` 能查到这个标签”拦不住。所以一律按 `type === "normal" && alwaysOnTop !== true` 判定能否分屏，挑“最后聚焦的 normal 窗口”时跳过 `alwaysOnTop` 窗口（v0.3 的 `openInOtherWindow`、`cycleRight` 同样适用）。PiP 文档是 `about:blank`，本扩展菜单项本来就不出现。

### 3.8 失败与降级（汇总）

| 情况 | 行为 |

### 3.10 隐私与对外文字

**CWS 数据使用披露**（我的决定）：在 v0.3 的“Web history”之外，**加勾“Website content”**，其余七类仍不勾。这是按 CWS 用户数据政策必须做的披露，不是可选项（理由见下）；它不影响要实现的代码，只在上传时于控制台勾选，上传前的检查清单里请用户过目一次即可。

**文档按“当前版本的完整状态”写**（我的决定）：v0.3 还没上传商店，v0.3 是先单独发还是跳过直接发 v0.4，由用户在发布时决定（第 6 节）。为了两种情况都不用返工，隐私政策、速查表、商店详情一律只描述 v0.4 的完整做法，不写“v0.3 → v0.4 的变更”小节；版本间的差别只写在 `CHANGELOG.md` 的各版本条目里（隐私政策“政策变更”一节的承诺由它兑现）。

为什么这样才诚实：

- CWS 的 Website content 类别举例是“text, images, sounds, videos, or hyperlinks”；用户数据 FAQ 把“information about the website content or resources”列为 handle 的例子，并且 handle 包括 transmitting（F16）。
- ② 读取的是网页上的文字（选区），⑧ 读取的是网页上图片资源的网址，两者都会经由右侧标签的网址发给一个外部服务（用户选的引擎）。这正是“处理网站内容并传输”。只靠“是用户主动点的”不能把它排除在外，FAQ 第 3 条连本地处理都要求披露。
- 不勾的风险：v0.3 的给审核员说明写着“does not read page content”，v0.4 新增 `contextMenus` 后审核员很容易看出这句不再成立，按披露不完整处理。
- Web history 继续勾：⑦ 经 activeTab 读当前标签网址，记录在 `storage.session` 里保留关键词，理由和 v0.3 相同。
- User activity 不勾：扩展不监听点击、按键或滚动。菜单点击是 Chrome 派发的事件，扩展只收到选区和图片网址，与 v0.3 对快捷键的处理同理。
- Personal communications、Personally identifiable information 不勾：选中的文字可能来自邮件或含个人信息，但扩展只处理用户自己选中并要求查询的那一段，不把它当作通信内容或个人信息收集、识别，这一点在 Website content 的说明里讲清楚。
- 合规声明（Limited Use）仍可全部勾选：发给引擎是面向用户的功能本身，符合单一用途。

**单一用途 (a)** 改写：从“地址栏和拖拽搜索时两个引擎并排”扩展为“在 Chrome 拆分视图里并排打开搜索结果：两个引擎的结果并排，或用户正在看的页面旁边放一个搜索或以图搜图结果”。弹窗补成分屏和右键菜单都列为服务这一用途的功能。

**权限理由 (b)** 新增两节（英文初稿，终稿走文案流程）：

- activeTab：When the user clicks the toolbar icon, Chrome temporarily grants access to the current tab. The popup uses it only to read that tab’s URL, to check whether the page is a search results page of one of the user’s engines and to read its search terms, so the user can open another engine’s results next to it in a split view. The URL is used on the device only; it is not stored or sent anywhere. Choosing one of the extension’s context-menu items, or pressing its keyboard shortcut, also grants this access as a side effect of Chrome’s design; the extension does not use it there. No content scripts are injected.
- contextMenus：Adds two items to the right-click menu on http(s) pages: one on selected text and one on images that have a public http(s) address. When the user chooses an item, the extension opens the selected text, or the image’s address, in the search engine the user picked on the settings page, next to the current page (in a split view when possible). It reads only the selected text or image address that Chrome passes with that click. The page’s own URL is not read or stored.

**隐私政策 (f) 与速查表要改的说法**：

- 新增：只有你在右键菜单里选了本扩展的菜单项时，扩展才读取你选中的文字或那张图片的网址。文字只发给你选的查词引擎，图片网址只发给你选的以图搜图引擎，由引擎服务器自己下载图片；页面网址不发（这句要等 S10 确认扩展发起的导航不带 Referer）。选中的文字和图片网址作为“这一次查询”暂存在浏览器内存里，用来在弹窗里显示和换右侧引擎，关闭标签或浏览器即清除。

- 删掉：“扩展不读取……网页内容”“does not read page content (no content scripts)”。保留“没有内容脚本”。
- 小标题：v0.3 的“数据只留在你的设备上 / your data stays on your device”在 v0.4 不够准确（选中文字会按你的要求发给引擎）。改成“不发给开发者或其他第三方；你要查的内容只发给你选的引擎”这一层意思（我的决定），4 种语言详情的【隐私】段第一句、README 隐私段同步改，具体措辞走文案流程。

- `storage.session` 字段清单补 `role`、`input`；`storage.sync` 字段清单补 `lookupEngine`、`imageEngine`、`imageEngines`。

**给审核员的英文说明**：在 v0.3 的段落基础上，第一句改成“Data usage: “Web history” and “Website content” are selected.”，删掉“page content (no content scripts)”里不读页面内容的意思，加两条：右键菜单只读选区或图片网址并只发给用户选的引擎；activeTab 只读当前标签网址，不存。
