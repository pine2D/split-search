一句话：设置页“默认组合”卡里有一个有序的规则列表，每条规则是“一个条件 → 一个右侧引擎”。条件有两种：搜索里有这些词，或搜索里有某种文字。地址栏、拖拽触发**默认组合**时，go.html 在本地拿关键词从上往下比，第一条命中的规则换掉右侧，左侧不动。

## 1. 意图

默认组合是固定的一对，比如 Google ｜ Bing。但用户搜不同的东西，想在右边看的引擎不一样：搜中文想看百度，问问题想看 Perplexity，查前端想看 MDN。现在只能另建网站搜索、换快捷字词（“其他组合”），或者分屏后在弹窗里手动换。⑥ 让常用的那几种情况自动换好，右侧仍然可以一键换回。

为什么放在 go.html：关键词只在本机出现过一次，就是 go.html 解析触发网址时（go.js:104、trigger.js:47–52）。在这里比，不用联网，不用多读存储，也不用存查询词。

### 1.1 目标

- K1：用户在设置页写几条规则，地址栏和拖拽搜索时右侧按规则换，左侧不变。
- K2：多语言用户三分钟内能配出最常见的一条：“搜索里有汉字 → 百度”。百度从设置页的右侧引擎库一键添加（lib/engine-catalog.js:44 已有 `baidu`），不用手写模板。
- K3：用户能看出右侧是规则换的、因为哪个词换的，并能一键换回。
- K4：全新安装没有规则，行为、存储形状、记录形状都与 v0.4 完全相同。
- K5：规则只是配置。判断全在本机，查询词不进 `storage.sync`、`storage.local`、日志。

### 1.2 非目标（v0.5 不做）

- 正则、通配、“不包含”、“同时满足”、前缀写法（`!w`）、“开头是”。
- 内置的“是问句”“像代码”判别器。“是问句”列为 v0.5.x 候选，“像代码”不做（见附录 A）。
- 繁简转换、同义词、词形变化（`run` 不命中 `running`）。
- 按历史学习、命中次数统计、“最近用过”。
- 规则作用于 ② 右键查词、⑧ 以图搜图、弹窗换右侧、快捷键轮换（第 9 节）。
- 规则换左侧。
- 工具栏角标提示（第 8.3 节末尾）。
- 模式 B 及其任何变体（“默认不分屏，按关键词才分屏”）。2026-10-24 已取消，本稿不提。

### 1.3 反目标（沿用 CLAUDE.md，这一版特别容易碰到的）

- 查询词或命中的词写进 `storage.sync`、`storage.local`、日志。
- **任何界面都不提供“以后这类搜索都用 X”“把这次查询存成规则”**。它会把一次真实查询变成同步的配置。弹窗只提供“换回”。规则里的每个词都必须是用户在设置页亲手写的。
- 规则改了左侧，或者改了 DNR，使 G5 降级（没装扩展、扩展失效时的普通左侧搜索）跟着变。
- 加权限、注入内容脚本、读页面内容。
- 规则让整次分屏失败。规则出任何错，都退回 `_ss` 原来的右侧（第 8.1 节）。
- 设置页刚精简过（`2026-10-27-engine-row-design.md`），不能回潮：没规则的用户在设置页上只多看到一行收起的 summary。

## 5. 匹配语义

### 5.1 规范化 `normalizeText(s)`

查询词和规则词用同一个函数：

1. `NFKC`（全角字母数字转半角、半角片假名转全角、U+3000 转空格）；
2. 去掉拉丁字母上的变音符：NFD 后把 `(\p{Script=Latin})\p{Mn}+` 换成基字母，再 NFC。只去拉丁字母的：日文浊点（が = か + U+3099）也是 Mn，不能去【我们的判断】；
3. `toLowerCase()`（不带 locale，结果不随系统语言变）；
4. 连续空白并成一个半角空格，trim。

所以 `ＷＩＫＩ`、`Wiki`、`wiki` 一样，`cómo` 和 `como` 一样。天气和天氣不一样，要分别写【我们的判断】。

查询词先粗截前 4000 码点再规范化，规范化后只比前 1000 码点【我们的判断】。规则词最长 32 码点，1000 足够；这样地址栏塞再长的文字 go.html 也不卡。

### 5.2 “这些词”：词边界

- 连写字符 `JOIN` = `[\p{L}\p{N}\p{M}]`，但不含不用空格分词的文字 `UNSPACED` = `\p{Script=Han}`、`Hiragana`、`Katakana`、`Hangul`、`Thai`、`Lao`、`Khmer`、`Myanmar`。
- 词的第一个字符是 `JOIN` 时，它在查询里的前一个字符（如有）不能是 `JOIN`；最后一个字符同理。
- 词的端点不是 `JOIN`（`UNSPACED` 字符、标点、符号如 `$` `#`、空格）时，那一端不查边界【我们的判断】（第 15 节第 32 条）。
- “前一个字符”“后一个字符”按码点取，不按 UTF-16 单元：往前取时遇到低代理就再退一个单元，往后用 `codePointAt`。扩展区汉字（如 𠀀）、emoji 是代理对，按单元取会拿到半个字符、判错边界【我们的判断】（第 15 节第 31 条）。词端点自身同样按码点取。
- 同一词出现多次，任一处两端都合格即命中。用 `indexOf` 循环，不用正则（第 7.3 节性能守门）。

效果：`py` 不命中 `happy`，命中 `happy py`；`python` 命中 `python教程`；`百科` 命中 `苏轼百科`；`서울` 命中 `서울에서`（韩文助词黏着，按子串，评审指出 minimal 漏了这条）；`c++` 命中 `objective-c++ 模板`；`3d` 不命中 `13d`；`2026` 命中 `2026年`；`c语言` 不命中 `abc语言`、命中 `学c语言`。

一条规则里的多个词是“任一”。词可以带空格（`how to` 是一个词）。

### 5.3 “某种文字”

有一个这种字符就算【我们的判断】。用 `Script`，不用 `Script_Extensions`：后者会让“、。”这类共用标点也算汉字。

| 值 | 界面名 | 判定 |
|---|---|---|
| `han` | 汉字 | `\p{Script=Han}` |
| `kana` | 日文假名 | `[\p{Script=Hiragana}\p{Script=Katakana}]` |
| `hangul` | 韩文 | `\p{Script=Hangul}` |
| `cyrillic` | 西里尔字母 | `\p{Script=Cyrillic}` |

只列这四种【我们的判断】。日文搜索通常也有汉字，用户要把“日文假名”放在“汉字”上面；对话框的提示里写这一句。

### 5.4 顺序

- 从上往下，**第一条生效且命中的规则决定结果**。暂不生效的规则（第 6.3 节 `off`）当作不存在，继续往下。
- 命中的规则是“保持默认”（`keep: true`，右侧选“默认组合的右侧”）：结果就是当前默认右侧，停下，记录不写 `rule`。这让用户能写例外（示例第 1 条）。存标记而不是引擎 id，改了默认组合之后例外仍是例外（见待用户决定第 2 条，暂按推荐写）。
- 命中的规则存的引擎 id 恰好等于当前默认右侧（例如用户后来把默认右侧改成了它）：同样停下、保持默认，记录不写 `rule`。
- 两种条件混在同一个列表里，只按列表顺序，不分层【我们的判断】。per-engine 方案“先比词、再比文字”的两层在界面上看不见，评审认为用户无法自己核对。
- 空关键词（只输入了快捷字词）不比，右侧按 `_ss`。

## 6. 数据形状与存储

### 6.1 `storage.sync` 新键 `rightRules`

```json
{
  "rightRules": [
    { "id": "r1", "when": "words", "words": ["天气", "weather"], "keep": true },
    { "id": "r2", "when": "words", "words": ["mdn", "css", "js"], "engine": "mdn" },
    { "id": "r4", "when": "script", "script": "han", "engine": "baidu" }
  ]
}
```

- 数组顺序就是优先级。不存开关、名称、命中次数、时间【我们的判断】。不要总开关：删规则或把它移到底部就够了，评审认为总开关与删除重复。
- `id`：`/^r[1-9][0-9]{0,3}$/`，创建后不变。只在规则之间唯一，不进引擎 id 命名空间（两者存在不同字段，从不比较）。
- `when`：`"words"` | `"script"`。`words` 只在 `when === "words"` 时有，`script` 只在 `when === "script"` 时有。
- `words`：存**规范化后**的词，用户看到的就是被比较的样子；规则内去重保留首次。
- `engine`：文字引擎 id（`ID_PATTERN`），不能是以图搜图引擎。
- `keep`：只能是 `true`，表示“保持默认组合的右侧”（例外规则）。每条规则 `engine` 与 `keep` 恰好有一个。不用 `engine: "default"` 之类的保留 id：`default` 符合 `ID_PATTERN`，可能撞上用户的自定义引擎 id（见待用户决定第 2 条，暂按推荐写）。

键不存在 = 没有规则。规则删光时 `removeKeys(["rightRules"])`，存储回到全新安装的形状。

### 6.2 上限与配额

| 项 | 上限 | 错误码（新，`err_<code>` 四语） |
|---|---|---|
| 规则条数 | 20 | `rule_too_many` |
| 每条词数 | 30 | `rule_too_many_words` |
| 全部规则的词合计 | 60 | `rule_words_total` |
| 每个词 | 32 码点（规范化后） | `rule_word_long`（带 `$WORD$`，显示前 12 码点） |
| 至少一个词 | ≥1 | `rule_no_words` |
| 文字类型 | 四种之一 | `rule_script` |
| 右侧引擎 | “默认组合的右侧”（`keep`），或未隐藏的文字引擎、不是默认左侧；编辑时等于这条规则原来的引擎也放行（即使已隐藏，见第 8.6 节） | `rule_engine` |
| 序列化后字节 | 8000 | `rule_too_large` |

- 字节：保存前在 `rule-edits.js` 里算 `new TextEncoder().encode(JSON.stringify(rules)).length + "rightRules".length`，超过 8000 就在对话框的词字段上报 `rule_too_large`，不等 saveKeys 报通用的 `config_too_large`（评审意见）。
- 估算：骨架约 70 字节/条，20 条约 1.4 KB；60 个 32 字的汉字词约 60 × 99 ≈ 5.9 KB，合计约 7.3 KB。全是 4 字节 emoji 的词才会超，由字节检查拦下。正常用法（5 条、10 个词）约 400 字节。
- 写入频率：新增、保存、上移、下移、删除各写一次，远低于每分钟 120 次。

### 6.3 读时清洗（`mergeConfig` 里）

`mergeConfig`（engines.js:56–109）多返回 `rightRules = cleanRules(stored.rightRules, { engines, hidden, defaultPair, isEngineId })`，每条形如 `{ id, when, words?, script?, engine?, keep?, off }`：

- 不是数组 → `[]`；元素不是对象、`id` 不合法或重复、`when` 不认识、`script` 不认识、`engine` 格式不对 → 丢掉这条；
- `keep === true` → 这条是“保持默认”，丢掉 `engine`（两者都有时以 `keep` 为准），`off` 恒为 `null`；`keep` 不是 `true` 又没有合法 `engine` → 丢掉这条；
- `words` 逐个重新规范化、去空、去重、丢掉超长的，每条截到 30 个、合计截到 60 个（前面的规则优先）；一个都不剩 → 丢掉这条；
- 超过 20 条只留前 20；
- `off`：`null`（生效）、`"hidden"`（引擎已隐藏；只有预置引擎能隐藏，engines.js:60–66，自定义引擎只能删除）、`"missing"`（找不到这个文字引擎，含以图搜图引擎 id、别的设备同步来的孤儿 id）、`"left"`（等于当前默认左侧）。
- 不删存储：隐藏的引擎恢复、默认左侧换掉后，规则自动重新生效。
- `isEngineId` 由 engines.js 传入，`lib/right-rules.js` 不 import engines.js，避免循环引用。

### 6.4 `storage.session` 记录多两个字段

只在搜索对、只在显示规则引擎的那一侧（右侧）记录上：

```
{ peer, splitViewId, mode, role: "search", engine: "mdn", query, rule: "r2", base: "bing" }
```

- `rule`：规则 id；`base`：没有规则时本来的右侧（`_ss` 的右侧 id）。都是配置 id，不是新的隐私数据。命中的词不存，弹窗按 id 找到规则后用 `query` 在本地重算（第 8.3 节）。
- **parseRecord**（split-owner.js:17–28，白名单返回）：只有 role 为 search 时放行；`rule` 匹配 `RULE_ID`、`base` 匹配引擎 id 格式且不等于 `engine`，三者都满足才保留，否则**两个一起丢掉、记录照常返回**。坏的附加字段不能让记录变成“无记录”，那会改变归属判定。page / lookup 角色忽略这两个字段。split-owner.js 不 import right-rules.js，`RULE_ID` 在本地写一份（与 right-rules.js 的同名常量由测试比对相等）。
- **makeRecords**（split-owner.js:34–45）：多可选参数 `autoA`、`autoB`（`{ rule, base }` 或 undefined），只在搜索对时写进对应一侧。
- **writePair**（split-state.js:33）：解构并透传 `autoA`、`autoB`。
- **writeEngine**（split-state.js:46–54）：写 `{ ...record, engine }` 时**去掉 `rule`、`base`**。用户经弹窗或快捷键换过右侧，就不再是规则选的。

## 9. 范围问题的结论

**Q1 作用于哪些入口**

| 入口 | 结论 | 理由 |
|---|---|---|
| 地址栏、拖拽、Chrome 自带右键“使用 X 搜索”（都经 go.html） | **生效** | 这就是 ⑥。go.js 一处插入，new / reuse / join / foreign / other-window 五个分支全覆盖 |
| ② 右键查词 | **不生效**【我们的判断】 | 菜单标题写着引擎名：menu-spec.js:12–14 的 `menuItems` 用 `textEngine.name` 填 `menu_lookup_text`（“在拆分视图中用 $ENGINE$ 搜索“%s””）。菜单只在安装、启动、sync 变化时重建，Chrome 不能按选区在弹出前改标题。按规则换引擎，菜单写的和实际打开的就对不上。想让查词换引擎，“右键查询”卡已经能选。另外，查询对的记录还要放行 `rule`/`base`，改动面更大 |
| ⑧ 以图搜图 | 不适用 | 没有关键词 |
| ⑦ 补成分屏 | **只影响建议排序**【我们的判断】 | 第 8.4 节 |
| 弹窗换右侧 | 不生效 | 每次都是用户亲手点。规则只提供“换回” |
| 快捷键轮换 | 不生效 | 轮换是用户主动换下一个，从当前（可能是规则选的）右侧往后走 |

**Q2 显式组合**：不生效【我们的判断】。只有 `_ss` 的左右都等于当前 `defaultPair` 才比。“其他组合”生成器的初值故意避开默认组合（edits.js:18–29），用户另建网站搜索就是想固定那一对；这也给了用户一个绕开规则的办法。备选“右侧等于默认右侧就生效”（detectors）被否：更难用一句话讲清。固有限制：`_ss` 里没有“这是默认组合”的标记（trigger.js:7–12），用户改了默认组合、没在 Chrome 里更新网站搜索时，旧条目会被当成显式组合，规则不生效。intro 里写了“其他组合不受影响”，“添加到 Chrome”卡原本就提示改了组合要更新网址。不往 `_ss` 里加第三段：旧网址和同步设备上的旧版本会解析失败。

**Q3 用户怎么知道、怎么换回**：弹窗写明因为哪个词或哪种文字换的，加“换回 <原右侧>”（第 8.3 节）。换回、手动换、轮换都会去掉标记。分屏里不显示任何东西。不做“这次不用规则”的地址栏语法（会占用关键词前缀）。

**Q4 顺序与冲突**：一个有序列表，两种条件混排，第一条生效且命中的胜出；同一条里的词是“任一”。上移/下移调整。`shadowedWords` 提示被挡住的词（不拦保存）。右侧选“默认组合的右侧”的规则（`keep`）= 命中后保持默认，可作例外，改了默认组合仍是例外（见待用户决定第 2 条，暂按推荐写）。

**Q5 规则的引擎被删或隐藏**：隐藏 → 规则保留、暂不生效、行内说明，恢复后自动生效；删除 → 连带删掉，提示写条数，删除前在引擎对话框里能看到条数；sync 从别的设备来的孤儿规则 → 读时判 `missing`、暂不生效。规则引擎成了默认左侧 → `left`、暂不生效。暂不生效的规则在 go.html 里都当作不存在，继续往下找。

**Q6 与 cycleExclude、lookupEngine**：相互独立。规则可以选不参与轮换的引擎（比如引擎库加进来、默认排除轮换的 AI 引擎），轮换照常从它往后找；cycleExclude 不影响规则。`lookupEngine` 的“跟随默认组合右侧”跟的是 `defaultPair[1]`（engines.js:101–104），不跟规则结果。

**Q7 在本扩展的分屏里重新搜索**：生效【我们的判断】。复用是一次新搜索，按新关键词重新比：命中就把对侧换成规则引擎并写标记，没命中就换回默认右侧、去掉标记。这与 v0.4 一致（复用时右侧本来就按 `_ss` 改写，手动换过的右侧也会被换回）。窄窗口相邻对、join 走同一条 refreshPair。只改记录确认属于本扩展的那一侧，归属判定不变。不做“手动选过就粘住”。
