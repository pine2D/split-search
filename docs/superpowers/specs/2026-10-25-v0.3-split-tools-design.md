# Split Search v0.3：分屏状态加固、右侧引擎库、窄窗口降级、工具栏弹窗与快捷键

> 状态：待用户审批（2026-10-25）。
> 依据：2026-10-25 的头脑风暴与调研（只读代码摸排、Chrome 一次性原型、网上资料核实），以及三份独立的审阅意见（实现、测试、隐私与反目标）。
> 标“（用户决定）”的是用户在 2026-10-25 的选择；标“（我的决定）”的是设计者代为决定的细节，审阅时重点看。

## 1. 意图

v0.2 已经能从地址栏和拖拽打开分屏。v0.3 让分屏“打开之后”更好用，并且不加任何权限：

- 分屏打开后，能把右侧换成别的引擎，不用重新搜索（弹窗、快捷键）。
- 右侧可以放的东西更多：翻译、词典、视频、代码、地图、学术等，从设置页的引擎库一键添加。
- 窗口太窄时不硬塞两栏。
- 修掉“本扩展分屏”判定里的几个缺口，避免覆盖用户自己的标签。引擎库会让引擎 origin 变多，这一步必须先做。

路线图上的位置见 CLAUDE.md“路线图”。v0.3 做头脑风暴里的 ③⑤④①，v0.4 再加 `activeTab`、`contextMenus`。

### 1.1 目标

- **V1 分屏状态加固**：只有本扩展建出、并且仍是同一个分屏的两个标签，才算“本扩展分屏”。拆开后再拼回去、`splitWithTabId` 失败退化成普通标签等情况，一律不算。
- **V2 右侧引擎库**：设置页列出经过真机验证的模板，点一下就添加为自定义引擎。
- **V3 窄窗口降级**：窗口宽度不足时，右侧改在相邻的后台标签打开，不建分屏；设置页可以关掉这个行为。
- **V4 工具栏弹窗**：显示当前关键词和左右引擎，可以把右侧换成任一引擎；保留“打开设置页”的入口。
- **V5 快捷键**：一个命令“右侧换成下一个引擎”。默认不绑定，由设置页引导用户去绑（用户决定）。参与轮换的引擎可以在设置页里逐个选（用户决定）。

### 1.2 非目标（v0.3 不做）

- **弹窗或快捷键里的“互换左右”“拆开分屏”。** Chrome 原生已有“互换位置（Reverse position）”和“取消分屏（Separate split view）”，不重复做（用户决定）。
- 任何新权限（`activeTab`、`contextMenus`、`tabs` 都不加）。“把现有搜索补成分屏”“边读边查”“以图搜图”留给 v0.4。
- 按关键词自动选右侧（之后的版本）。
- 从网络更新引擎库。目录只写在代码里，唯一允许的 `fetch` 仍是读取包内的 `_locales`。
- 改分割比例、改上下或左右方向（扩展 API 没有这类接口）。
- 宣传图（`assets/templates`）不改。要不要加一张弹窗截图，以后由用户决定（我的决定）。

### 1.3 反目标（沿用 CLAUDE.md，这一版本特别容易碰到的几条）

- 覆盖用户手动建的分屏里的页面，包括“用户把本扩展的两个标签拆开、各自浏览后又拼回去”这种情况。
- 查询词离开本机，或进入 `storage.sync`。
- 为引擎库条目申请宽泛的 host 权限，或在用户没点授权时申请权限。
- 快捷键占用 Chrome 自带的快捷键，或在用户没绑定时就生效。

## 2. 已核实的事实（2026-10-25）

本机 Chrome 是 **156.0.8078.47**。CLAUDE.md 写的 155.0.8059.84 已过时，实现时顺手更新那条已知事实。`minimum_chrome_version` 保持 `"155"`。下表除注明外都在 156 上实测，155 上没有单独验证。

| 事实 | 来源 |
|---|---|
| `tabs.create({splitWithTabId})`：源标签在左，新标签在 `index+1`，两者拿到同一个 `splitViewId`。对已在分屏中的标签调用，报 `Tab ID … is already in a split view.` | 原型 Q1 |
| 跨窗口建分屏时，`tabs.create` 必须带 `windowId`，否则报 `mismatching 'windowId' states`。现有代码已经带了 | 原型 Q8 |
| 用 `tabs.move` 对调分屏里的两个标签：分屏不解散，`splitViewId` 不变，只触发 `onMoved`。把其中一个移到远处，分屏就解散 | 原型 Q2 |
| `tabs.unsplit(splitViewId)` 或关掉一侧：剩下的标签收到 `onUpdated {splitViewId:-1}` | 原型 Q3、Q4 |
| `createSplit` 每次分配新的 `splitViewId`；左右只由标签顺序决定 | 原型 Q5 |
| 对分屏里的标签 `tabs.update({url})`：分屏保留，`splitViewId` 不变 | 原型 Q6 |
| 没有 `tabs` 权限、也没有该 origin 的 host 权限时，`tabs.query` 结果里没有 `url`、`title` | 原型 Q7 |
| `tabs.onUpdated` 不接受过滤器，传了会抛 `This event does not support filters` | 原型 Q9 |
| `windows.get` 不需要 `tabs` 权限，就能读到 `width`（DIP，含窗口边框）、`type`、`state` | 原型 Q8 |

### 2.1 现有代码里的缺口（V1 要修）

- **记录从不清除。** `storage.session` 只存 `split:<tabId> → peerTabId`（`src/chrome/split-actions.js` 的 `recordPair`）。
- **拆开再拼回去会被覆盖。** 判定 `reuse` 只看 `recordedPeerId === peer.id`（`src/lib/split-decision.js`）。用户把本扩展的一对标签拆开，各自浏览后又拼成分屏，再触发一次，另一侧的用户页面就会被覆盖。
- **退化成普通标签后仍写了记录。** `createPaired` 在 `splitWithTabId` 抛错时退化成普通相邻标签，但 `openNew` 照样调用 `recordPair`。结果两个不在分屏里的标签留下了配对记录，用户之后把它们手动拼起来，同样会被覆盖。
- **兜底判定只看 origin。** 浏览器重启后没有记录，兜底只看另一侧网址的 origin 是否属于任一已配置引擎。引擎库加入 YouTube、GitHub、Amazon 等站点后，只要该 origin 已授权，用户手动拼的“YouTube 视频 + 别的页面”也会被当成本扩展分屏覆盖掉。

## 3. 设计

### 3.1 V1 分屏状态加固

**记录形状**（我的决定）：`storage.session` 的键仍是 `split:<tabId>`，值改成对象：

```
{ peer: <另一侧 tabId>, splitViewId: <建立时的 splitViewId，相邻标签模式为 -1>, mode: "split" | "adjacent", engine: <这个标签显示的引擎 id>, query: <关键词> }
```

- **每个标签记自己显示的引擎（`engine`），不记“左/右”。** 左右只看当前标签顺序：index 小的在左，沿用 `sideOf`。这样用户用原生“互换位置”之后，弹窗显示的和“换右侧”作用的，都是**看得见的右侧**，并且知道那个标签现在显示的是哪个引擎。
- **关键词存进 `storage.session`**（用户决定：存进浏览器内存，同步改隐私文案，见 3.6）。只在本机内存里，不写 `storage.sync`，不外发；浏览器关闭即清除。按 Chrome 文档，扩展重新加载、更新、停用时也会清空。
- **形状不对的值一律当作没有记录。** 例如旧版本留下的裸数字。因为 `storage.session` 在扩展更新时会清空，所以不做迁移。
- `mode: "adjacent"` 只用于窄窗口降级（3.3）。

**归属判定**：用一个纯函数（放 `src/lib/`，带 node 测试）统一判定“这一对是不是本扩展的”。go.html、弹窗、快捷键三处共用它，保证三处结论一致（我的决定）。输入是当前标签、对侧标签、两侧各自的记录、已配置的引擎；输出是“本扩展分屏 / 本扩展相邻对 / 不是 / 无记录需兜底”。规则：

1. **有当前标签的记录，并且记录有效**：`record.peer === 对侧.id`；对侧记录存在且 `peer` 指回当前标签；`mode` 为 `split` 时两条记录的 `splitViewId` 都等于当前 `splitViewId`（且不为 -1）；`mode` 为 `adjacent` 时两个标签都不在分屏中、在同一窗口里，且标签序号恰好相差 1。满足就算本扩展的。
2. **有当前标签的记录，但对不上**（例如拆开后又拼回去，`splitViewId` 变了）：直接判 **不是**，不再走兜底（我的决定）。有失效记录，说明扩展知道这一对已经解散过，这正是反目标里“拆开、各自浏览又拼回去”的情况，宁可多开一对标签。
3. **当前标签没有记录，但对侧有记录**（拆开后当前标签另组过一对、记录被连带清掉）：同样判 **不是**，不走兜底（2026-10-25 终审修正）。
   **两侧都没有记录**（典型情况是浏览器重启后）：走兜底。只有读到了对侧的 `url`，并且它**像某个已配置引擎的搜索结果页**，才算本扩展分屏（我的决定）：
   - 模板的 `%s` 在查询参数里：对侧网址的 origin 和 `pathname` 都与模板相同。比如 Google 的 `/search`、YouTube 的 `/results` 算，YouTube 的 `/watch` 不算。
   - 模板的 `%s` 在路径里：origin 相同，并且 `pathname` 以模板 `%s` 之前的那段路径开头，比如 Google 地图的 `/maps/search/`。
   - 拿“任一已配置引擎”的模板去比，与现状的范围相同，只是从比较 origin 收窄到比较搜索页路径。
   - 代价：引擎跳到同 origin 的别的路径（例如 consent 页）时，兜底判成“不是”，结果是多开一对标签，不会覆盖页面，可以接受。
   - 读不到 `url` 或无法判定时，判“不是”（不变）。
4. 兜底判成本扩展分屏后照常执行 `reuse`，并按新形状写入两条记录。这与 v0.2 一致，v0.2 的 `reuse` 也会调用 `recordPair`。写入后，重启之后的这一对也能用弹窗和快捷键。

**只在真的建成分屏时写 `split` 记录**：`createPaired` 返回新标签后，核对它的 `splitViewId !== -1`，并重新读一次当前标签的 `splitViewId`。两者相同且不为 -1 时才写记录，记录里的 `splitViewId` 用这个值。退化成普通标签时不写，并在 console 记一条 `[split-search]` 日志（可以和现有的退化日志合并）。

**清理**（我的决定。头脑风暴时说的是监听 `onUpdated`，这里改了，请留意）：

- **不监听 `onUpdated`。** 它不能过滤，监听就意味着用户每个标签的每次加载都会唤醒 SW。上面第 1、2 条的核对已经保证了安全，判断不依赖监听。
- **SW 顶层监听 `tabs.onRemoved`。** 标签关闭时删掉它自己的记录。对侧的记录，只有在它指回被关掉的标签时才删，避免误删对侧已经和别的标签重新建立的有效记录。
- **用到时顺手清理。** go.html、弹窗、快捷键读到失效记录时，只有记录里的对侧标签已经不在了，才按同样的“指回才删”规则顺手删掉；对侧还在时两条记录都保留，让用户拆开后再拼回去的这一对一直判“不是”，不会落到兜底被覆盖（2026-10-25 终审修正）。
- 残留记录不影响正确性，只占很少的 `storage.session` 空间（上限 10 MB）。

### 3.2 V2 右侧引擎库

**数据**：新文件 `src/lib/engine-catalog.js`，只放纯数据和纯函数，不碰 `chrome`。每个条目的形状：

```
{ id, name, url, category, leftDiscouraged?, ai? }
```

- **`name` 一律用拉丁写法的品牌名，不翻译**（我的决定），例如 Google Translate、Google Maps、Bilibili、Baidu、Zhihu。理由：`test/i18n-catalog.test.js` 要求 `src` 代码里没有汉字，CLAUDE.md 也禁止在代码里写界面文字，与 `PRESETS` 的做法一致。添加之后用户可以自己改名。
- **分类名走 i18n**，key 是 `catalog_cat_<分类>`。在代码里写成字面量映射，不动态拼接。
- **扩充 `test/i18n-catalog.test.js` 的 `KEY_RE` 前缀表。** 加上本版新增的前缀（例如 `catalog`、`popup`），否则新 key 会被报成“未被引用”。
- **`url` 里可以有两个占位**：`<target>` 表示翻译目标语言，`<lang>` 表示 Wikipedia 的语言子域名。添加时按当前界面语言展开（我的决定）：
  - `<target>`：en→`en`，zh_CN→`zh-CN`，zh_TW→`zh-TW`，es→`es`（各翻译站的语言代码写法不同，按条目各自映射）。
  - `<lang>`：en→`en`，zh_CN/zh_TW→`zh`，es→`es`。
  - node 测试对每个条目、每种界面语言都展开一次，逐个检查：通过 `validateTemplate`；id 符合 `ID_PATTERN` 且互不重复、不与任何预置 id 重复；origin 是精确 origin。
- 能不能作左侧不手写，由 `canBeLeft` 推出。
- `ai: true` 标出 AI 对话类条目，只用于决定是否默认参与快捷键轮换（3.5）。

**收录规则**：每个条目先在真机 Chrome（测试配置或一次性配置）里点一遍，确认打开后关键词已经填好或已经出了结果，并且不跳登录墙，才收录。实现计划里单列一个验证任务，结果记在附录 A。网上资料只能证明服务端会保留参数，证明不了页面会预填。

- **验证时同时看有没有 Service Worker 接管导航**（方法同 e2e 的 T14）。这只影响作左侧的情况：有接管的条目带上 `leftDiscouraged: true`。
- **自定义引擎要能持久化 `leftDiscouraged`**（我的决定）：
  - `customEngines` 的项可以带这个布尔字段。
  - `mergeConfig` 现在用 `{ ...c }` 原样复制字段，要改成主动清洗：只认 `leftDiscouraged === true`，其他值丢掉。
  - `editEngine` 现在会保留旧字段，要改成：模板的 origin 变了就去掉 `leftDiscouraged`。
  - 设置页的编辑对话框不提供这个开关，它只能从目录带进来。
  - 现有的“建议只作右侧”提示（引擎列表、默认组合卡片、组合生成器）自动覆盖这些条目。

**添加流程**：

- **入口**：设置页“搜索引擎”卡片加一个按钮“从引擎库添加”，打开对话框，按分类列出条目，每条显示名称和“添加”按钮。如果已经有模板相同的引擎（展开占位之后比较），就显示“已添加”，不可点。
- **添加的结果**：复制成一条自定义引擎（`customEngines`），之后能改能删，与目录脱钩。不做成预置，因为预置的 id 永久占用，只能隐藏、不能删。
- **id**：用目录里的 id；被占用时依次加 `-2`、`-3`……，直到不冲突且不超过 20 个字符。
- **位置**：加到显示顺序的末尾，不改默认组合。
- **授权提示**（我的决定）：
  - 从引擎库添加的条目，一律按右侧用途处理，添加时不显示“需授权”的持久警告。引擎行上保留授权按钮。
  - 手动新增一个不能作左侧的引擎，同样不再显示持久警告。这类引擎的授权只用于浏览器重启后的兜底判定，不是必需的。
  - 用户之后把这类引擎设成默认组合的左侧时，走现有的默认组合授权引导。
  - 手动新增能作左侧的引擎，维持现状。
  - DNR 规则不用改：`requestDomains` 里列了没授权的 host 也不会生效，重定向需要 host 权限。
- **存储上限**：`customEngines` 整个数组共用 8192 字节的单项上限（`config-store.js` 的 `MAX_ITEM_BYTES`）。添加前先算出写入后的大小，超限就不写，显示现有的 `config_too_large` 错误文案。不做分片（我的决定）：按每项约 120 字节估算，能放约 60 个，够用；以后真不够再分片。

**文件划分**：

- `options.js` 已有 242 行，新增的 action 放不下时，把 `actions` 拆到 `src/options/actions.js`。
- 纯逻辑（“已添加”判定、id 去冲突、占位展开、字节预检）放 `src/options/edits.js` 或 `src/lib/engine-catalog.js`，都要有 node 测试。

### 3.3 V3 窄窗口降级

- **阈值**（我的决定）：要建分屏的那个窗口 `width < 960` 就算窄。`width` 是 `windows.get` 的值，单位 DIP，含窗口边框。960 大约是 1920 宽屏幕的一半：Windows 贴边半屏时不分屏，因为两栏各约 480，搜索结果页基本会变成手机版式。常量放 `src/lib/`，带测试。
- **开关**：设置页“默认组合”卡片里加一个复选框“窗口较窄时，右侧改在后台标签打开”，默认勾选。`storage.sync` 新增顶层键 `narrowFallback`（布尔，没有这个键时按 `true` 处理）。不勾时一律分屏，行为同 v0.2。
- **窄窗口下各动作的放法**（我的决定）。三种情况都是右侧不传 `splitWithTabId`，都按 3.1 写 `mode:"adjacent"` 的记录：
  - `new`：右侧在当前标签右边相邻位置开**后台**标签（`active:false`），然后当前标签 `location.replace(左侧)`。
  - `foreign`：沿用现有做法。在用户分屏右边（`maxIndex+1`）新开左侧标签（`active:true`），右侧开在它右边相邻位置（后台）。当前标签按现有 `leaveTab` 回到原页面或关闭，不改写用户分屏里的页面。
  - `other-window`：沿用现有做法。在目标 normal 窗口里新开左侧，右侧开在它右边相邻位置；看的是目标窗口的宽度。
  - `reuse`：分屏已经存在，就地更新，不看宽度。
- **相邻对的复用**：同一个标签在窄窗口里反复搜索时，如果 3.1 判定它和右边那个标签是本扩展的相邻对，就就地更新右边那个，不再新开（我的决定），否则每搜一次就多一个标签。相邻对被用户拖开（不再紧挨着）后，就不再复用。窗口变宽到阈值以上或关掉开关后，同一个标签再搜索时，先更新右边那个，再用 `createSplit` 把这两个标签拼成分屏并改记 `split`；拼不成时退回相邻对的复用（2026-10-25 终审修正）。
- **不额外弹提示**（我的决定）：go.html 会立刻跳走，提示没有地方显示；右侧标签就在旁边，看得到。

### 3.4 V4 工具栏弹窗

- **manifest 与入口**：`manifest.json` 的 `action` 加 `default_popup: "popup/popup.html"`，删掉 `background.js` 里的 `action.onClicked → openOptionsPage`。首次安装时仍由 `onInstalled` 打开设置页。
- **文件**：新建 `src/popup/popup.html`、`popup.js`、`popup.css`。接入 `src/chrome/i18n.js`，跟随 `uiLocale`，`await i18nReady` 之后才渲染。样式沿用设置页的颜色变量，支持深色模式。
- **目标标签**：默认是弹窗所在窗口的活动标签（`tabs.query({active:true, currentWindow:true})`）。URL 带 `?tabId=<数字>` 时改用这个标签，这是给 e2e 留的测试接缝。`popup.html` 不在 `web_accessible_resources` 里，网页打不开它，所以这个参数不会扩大可操作的范围。
- **状态判断**：用 3.1 的归属判定函数。分屏和相邻对都支持。
- **显示**：
  - 是本扩展的：显示关键词（为空时显示说明“空关键词”的文案）、左侧引擎名、右侧引擎名（按当前标签顺序判断左右）。下面列出全部引擎（按显示顺序，当前右侧引擎除外），点一个就把右侧换成它。这里列全部引擎，不受快捷键轮换设置的限制，因为每一次都是用户亲手点选。底部是“打开设置页”。
  - 不是：一句说明（“当前标签不是 Split Search 打开的分屏”），加“打开设置页”。v0.4 的“补成分屏”会放在这里。
  - 记录里的引擎已被删除：显示为“已删除的引擎”，换右侧照常可用。
- **换右侧**：`tabs.update(右侧标签, {url: expandTemplate(新引擎.url, query)})`，再更新那个标签记录里的 `engine`。空关键词沿用 go.js 的规则（打开模板的 origin）。换完弹窗保持打开并刷新显示，方便连续切换。
- **读不到右侧标签的 url 也能换**：记录里有引擎 id 和关键词，不需要读网址，也就不需要 host 权限。
- **已知限制**：右侧已经被用户点进别的网站时，换右侧会把它覆盖掉。这和 v0.2 里 go.html 在本扩展分屏内的 `reuse` 行为一致（spec 5.3），接受。弹窗是用户亲手点选的，误触风险低；快捷键的误触风险由“默认不绑定”来控制（3.5）。

### 3.5 V5 快捷键

- **manifest**：加 `commands`，只有一个命令 `cycle-right`，描述走 `__MSG_cmd_cycle_right__`，**不写 `suggested_key`**（用户决定：默认不绑定）。`_execute_action` 也不绑定。
- **设置页引导**：加一行“快捷键”，用 `chrome.commands.getAll()` 显示当前绑定，没绑时显示“未设置”。旁边一个按钮，用 `tabs.create({url: "chrome://extensions/shortcuts"})` 打开 Chrome 的快捷键页。设置页获得焦点时刷新这一行，用户绑完回来就能看到。
- **参与轮换的引擎**（用户决定：设置页自选）：
  - 引擎列表里每个引擎加一个开关“参与快捷键轮换”。
  - `storage.sync` 新增顶层键 `cycleExclude: string[]`，存不参与轮换的引擎 id，没有这个键时视为空，即全部参与（我的决定）。
  - 从引擎库添加 `ai: true` 的条目时，同时把它的 id 加进 `cycleExclude`（我的决定）。AI 对话类服务可能自动发送，并把内容存进账号历史，所以默认不让快捷键路过它们。用户可以手动打开。
  - 删除引擎时，从 `cycleExclude` 里一并去掉，做法同 `deleteEngine` 对 `order` 的处理。
- **行为**：
  - SW 顶层监听 `commands.onCommand`。取最后聚焦的 normal 窗口的活动标签，按 3.1 确认这一对是本扩展的。
  - 是就把右侧换成显示顺序里、当前右侧引擎之后的**下一个**参与轮换的引擎：到末尾回到开头，跳过当前右侧本身，可以与左侧相同。
  - 没有可换的引擎，或这一对不是本扩展的，什么都不做，也不弹任何东西。
- **共用逻辑**：“下一个引擎”是纯函数，放 `src/lib/`，带测试。换右侧的执行逻辑在弹窗和 SW 之间共用，放 `src/chrome/` 下的薄封装（新文件，或并入 `split-actions.js`，注意 300 行上限）。

### 3.8 e2e
