# 多语言（i18n）设计与排期

日期：2026-10-24　作者：pine2D　状态：**已批准**（用户 2026-10-24 批准范围和第 13 节全部决定），可据此写实现计划（本文只写方案，不动代码）

## 1. 意图

用户已决定（2026-10-24 对话）：

- 首期 4 种语言：英文 `en`、简体中文 `zh_CN`、繁体中文 `zh_TW`、西班牙语 `es`。不做阿拉伯语和印地语。
- 设置页提供语言切换，默认“跟随浏览器”。
- 中文源文案先用 humanizer 和 lieflat-less-ai-tone 润色定稿，再翻译。
- `default_locale` 为 `en`；所有语言都叫 `Split Search`；`zh_TW` 按台湾用词；v0.2 = 多语言，模式 B 顺延到 v0.3；v0.3 时首次提交 CWS（第 13 节）。

扩展上架 Chrome 网上应用店（CWS）以后，用户不只是简体中文读者。目前设置页、go.html 出错页、manifest 简介和工具栏按钮标题都写死为简体中文，而设置页是每个用户都要走一遍的流程（授权、复制触发网址、添加网站搜索）。本方案把界面文案搬进 `_locales`，由扩展自带的小加载器按所选语言取用，并给每种语言出一份商店详情。

## 2. 首期语言

### 2.1 背景：使用人数排名

来源：Ethnologue 2026 版《The Ethnologue 200》，口径为母语加第二语言的总人数（L1+L2），数字转引自 Wikipedia “List of languages by total number of speakers” 的 “Ethnologue (2026)” 一节（2026-10-24 查阅）。Ethnologue 不算宏语言，所以第 2 名是官话，第 5 名是现代标准阿拉伯语。

| 排名 | 语言 | 总人数（百万） | 首期 |
|---|---|---|---|
| 1 | 英语 English | 1,493 | `en` |
| 2 | 官话 Mandarin Chinese | 1,183 | `zh_CN` 简体 + `zh_TW` 繁体 |
| 3 | 印地语 Hindi | 611 | 不做 |
| 4 | 西班牙语 Spanish | 561 | `es` |
| 5 | 现代标准阿拉伯语 Modern Standard Arabic | 335 | 不做 |

用户最初要“英文、繁体、简体及全球使用人数前五以内的其他语言”，随后决定去掉阿拉伯语和印地语，所以前五名里只多出西班牙语。

### 2.2 扩展包里的语言目录

CWS 支持的语言代码是固定列表（`chrome.i18n` 文档的 Locales 一节），列表以外的目录会被 Chrome 忽略。

| 目录 | 覆盖 | 说明 |
|---|---|---|
| `_locales/en` | 所有英语区 | 也是 `default_locale` |
| `_locales/zh_CN` | 简体中文 | 源文案 |
| `_locales/zh_TW` | 繁体中文 | 香港、澳门见 2.3 |
| `_locales/es` | 所有西班牙语区（含 `es_419`） | 中性写法，不用 vosotros |

### 2.3 繁体中文与香港

- 页内文案：语言由本扩展自己的 `resolveLocale()` 决定（5.3），`zh-HK`、`zh-MO`、`zh-Hant*` 一律映射到 `zh_TW`，不依赖 Chrome 的行为。
- manifest 级文案（简介、按钮标题）仍由 `chrome.i18n` 决定。CWS 列表里没有 `zh_HK`，香港用户能否用上 `zh_TW`，取决于 Chromium 是否把浏览器界面语言 `zh-HK` 归到 `zh-TW`（凭源码记忆推断，未实测）。影响只有这两行字，不单独做 spike。
- 用词按台湾惯例（網址、搜尋引擎、設定），不另外照顾香港用词（第 13 节决定 3），与 Chrome 自己的 zh-TW 界面一致；Chrome 菜单名照抄 Chrome 155 zh-TW 原文（第 10 节术语表）。

## 3. default_locale：`en`

`default_locale` 决定两件事：manifest 级文案在 4 种语言之外显示哪种，以及 CWS 详情的默认语言。页内文案的兜底也用它（5.3）。

已决定用 `en`（第 13 节决定 1）。理由：法语、德语、日语等界面的用户看英文比看简体中文好懂；CWS 对没有本地化详情的地区展示默认语言。作者仍以 `zh_CN` 为源文案，先写中文再出英文，二者不冲突。CWS 首次提交在 v0.3，那时扩展包已带 `_locales` 和 `default_locale`，不存在改默认语言的迁移问题。

## 4. 文案目录（messages.json）

### 4.1 位置与格式

`src/_locales/<语言>/messages.json`，Chrome 标准格式。每条都写 `description`，给翻译看上下文和长度限制：

```json
{
  "go_err_unknown_engine": {
    "message": "未知引擎：$ENGINE_ID$",
    "description": "go.html 出错页。触发网址里的 _ss 写了一个不存在的引擎 id。",
    "placeholders": { "engine_id": { "content": "$1", "example": "nope" } }
  }
}
```

### 4.2 命名

- key 只用 `[a-z0-9_]`（`chrome.i18n` 的 key 不区分大小写，统一小写避免撞名）。
- 前缀表示位置：`ext_`（manifest）、`go_`、`options_`、`engine_`、`guide_`、`notice_`、`err_`（错误码，见 5.5）、`common_`（取消、保存、复制、关闭等）、`lang_`（语言选择器）。
- 一句完整的话一个 key，**不准拼句子**：现在的 `confirmRemoval(e, "隐藏")`、`` `已${verb}“…”` `` 要拆成 `engine_confirm_hide`、`engine_confirm_delete`、`notice_hidden`、`notice_deleted` 等完整句子。

### 4.3 占位符

- 一律用具名占位符（`$ENGINE$`），`content` 写 `$1`…`$9`，`example` 必填，翻译可以自由调整语序。字面 `$` 写成 `$$`。
- 引擎名、网址、id、数字上限这些运行时值都走占位符。
- 引号、冒号、句末标点写在各语言自己的文案里（简体“”和全角冒号，繁体「」，英文 “ ”（撇号用 ’，与 Chrome en-US 界面一致；2026-10-24 用户决定），西班牙语 « » 或 " "），代码不拼标点。
- `${dl.name} ｜ ${dr.name}` 改为 `guide_pair_label`（`$LEFT$ ｜ $RIGHT$`），英文、西班牙语写 `$LEFT$ | $RIGHT$`。
- 左右选择框之间的装饰分隔符同样按语言取 `common_pair_separator`（中文“｜”，英文、西班牙语“|”），不在代码里写字面量。

### 4.4 规模

按 2026-10-24 本分支 `src/` 粗数约 160 条，拆掉拼句、加上语言选择器后按 175 条估算。`console.error` 开发日志不算界面文字，不翻译。

## 5. 取文案与页内语言切换（无构建、无依赖）

`chrome.i18n.getMessage` 只跟随浏览器界面语言，运行时换不了，所以页内文案改由扩展自带的小加载器读取 `_locales`。不引入 i18next 之类的库，也不做编译期替换。

### 5.1 manifest

```json
"default_locale": "en",
"name": "Split Search",
"description": "__MSG_ext_description__",
"action": { "default_title": "__MSG_ext_action_title__" }
```

`name` 保持字面量 `Split Search`：所有语言都用这个名字，商店名称也不加本地副标题（第 13 节决定 2）。这几处只能走 `chrome.i18n`。

**限制（写进设置页语言选择器的说明文字和 README）**：manifest 的简介、工具栏按钮标题、`chrome://extensions` 里的描述，以及 CWS 详情，都跟随浏览器或商店的语言，不跟随页内选择。

### 5.2 语言选择与存储

- 设置页顶部加一个“语言”下拉框。选项：“跟随浏览器（当前：English）”，然后是 `English`、`简体中文`、`繁體中文`、`Español`。具体语言一律用各自的写法显示，选错语言的用户也能认出自己的语言；只有“跟随浏览器”这一项和标签文字随当前语言翻译。
- 存在 `chrome.storage.sync` 的顶层键 **`uiLocale`**，值为 `"auto"`、`"en"`、`"zh_CN"`、`"zh_TW"`、`"es"`。键不存在或值不认识都按 `"auto"`。选择后立即经 `options.js` 现有的串行写入 `write(() => ({ ok: true, patch: { uiLocale } }))` 保存，走 `config-store.js` 的 `saveKeys`，只写这一个顶层键，不碰引擎配置。
- 与 `mergeConfig` 的关系：`mergeConfig(stored)` 在返回值里加 `uiLocale: normalizeLocalePref(stored.uiLocale)`（`normalizeLocalePref` 来自 `src/lib/i18n.js`，两者都是纯逻辑）。引擎、组合的合并逻辑不变。v0.1 的 `mergeConfig` 只解构自己认识的键，同步到旧版本设备时会忽略 `uiLocale`，不出错。
- 用 `storage.sync`，所以选择会跟着 Chrome 同步到用户的其他设备；各设备浏览器语言不同的用户保留“跟随浏览器”即可。
- 生效：`options.js` 已在 `storage.onChanged`（sync）时调用 `render()`。`render()` 发现 `uiLocale` 与已加载的不同时，先 `await setLocale(...)`，再 `applyI18n(document)` 重写静态文字，然后照常重建动态部分。不刷新页面；另开的设置页同样会跟着切换。已经弹出的提示保持原语言，自动消失即可。

### 5.3 两个新文件

**`src/lib/i18n.js`**（纯逻辑，不碰 `chrome`，有 node 测试）：

- `LOCALES = ["en", "zh_CN", "zh_TW", "es"]`，`DEFAULT_LOCALE = "en"`。
- `normalizeLocalePref(v)`：`LOCALES` 里的值或 `"auto"` 原样返回，其余返回 `"auto"`。
- `resolveLocale(pref, uiLanguage)`：`pref` 是具体语言就用它；`"auto"` 时把 `uiLanguage` 的 `-` 换成 `_` 后映射：`zh_TW`、`zh_HK`、`zh_MO`、`zh_Hant*` → `zh_TW`；其余 `zh*` → `zh_CN`；`en*` → `en`；`es*` → `es`；都不是 → `en`。
- `formatMessage(entry, subs)`：按 `chrome.i18n` 的规则替换：`$NAME$`（不区分大小写）换成 `placeholders[name].content`，其中的 `$1`…`$9` 换成 `subs[n-1]`（缺了给空串），消息里直接写的 `$1`…`$9` 同样替换，最后 `$$` → `$`。
- `splitMarked(text)`：把带标记的字符串切成“文字段 / 第 n 个节点”序列，供 `tNodes` 用（5.6）。

**`src/chrome/i18n.js`**（碰 `chrome.*`，放 `src/chrome/`）：

```js
let chosen = null, fallback = null;
const load = l => fetch(chrome.runtime.getURL(`_locales/${l}/messages.json`)).then(r => r.json());

export async function setLocale(pref) {
  const locale = resolveLocale(pref, chrome.i18n.getUILanguage());
  [chosen, fallback] = await Promise.all([load(locale), locale === "en" ? null : load("en")]);
  document.documentElement.lang = locale.replace("_", "-");
}
export async function initI18n() {          // go.html 和设置页的入口
  const { uiLocale } = await chrome.storage.sync.get("uiLocale").catch(() => ({}));
  await setLocale(normalizeLocalePref(uiLocale));
}
export function t(key, ...subs) { /* chosen → en → 记错误并返回 key */ }
```

- 兜底顺序：所选语言 → `en` → `console.error("[split-search] missing message", key)` 并返回 key 本身，让 e2e 的“无 [split-search] 控制台错误”抓到。两份文件都读不到时（理论上不会发生），`t()` 改用 `chrome.i18n.getMessage`（浏览器语言），并记一条错误。
- `applyI18n(root)`：扫描 `data-i18n="key"`（写 `textContent`）和 `data-i18n-attr="placeholder:key;aria-label:key;title:key"`（写属性），同时设置 `document.title`，最后去掉 `<html>` 上的 `i18n-pending`（5.7）。
- `tNodes(key, nodes)`：带内联元素的句子（5.6）。
- 两个文件都远低于 300 行。`messages.json` 每份约 30～40 KB，每页最多读两份。

### 5.4 fetch 与隐私承诺

`fetch(chrome.runtime.getURL(...))` 读的是 `chrome-extension://<id>/_locales/...`，即扩展包自己的文件，由浏览器从本地安装目录读取，不产生任何网络流量，也不是远程代码（读的是 JSON 数据）。因此商店详情和隐私政策里“不发网络请求”的说法仍然成立，不用改。

实现时只需同步改 `docs/store/privacy.md`“代码事实速查”里“没有 `fetch`”那一行，改成“唯一的 `fetch` 读取扩展包内的 `_locales/*/messages.json`（`chrome-extension://` 地址），没有任何外部请求”，核对方式改为第 9.1 节的静态检查。go.html 经 `use_dynamic_url` 重定向后最终落在静态 id 网址（CLAUDE.md 已知事实），与 `runtime.getURL` 同源，MV3 默认 CSP 不限制读自身资源；冒烟步骤会实际打开 go.html 出错页，等于顺带验证这一点。

### 5.5 `src/lib` 和 `edits.js` 返回错误码，不返回句子

`src/lib/` 不能引用 `chrome`，拿不到 `t()`。`validateTemplate`、`parseTrigger`、`addEngine` 等现在返回中文句子，改为返回错误码和参数，由页面层翻译：

```js
return { ok: false, error: { code: "unknown_engine", args: [ids[i]] } };   // lib
showError(t("err_" + parsed.error.code, ...parsed.error.args));            // 页面
```

`throw new Error(...)` 的地方（`trigger.js`、`config-store.js` 的“配置过大”）给 Error 加 `code` 属性；`ui.js` 的 `errorText()` 对配额错误同样返回 key。错误码集中导出为 `ERROR_CODES`，catalog 测试据此检查每个码都有 `err_<code>`。单元测试随之改为断言错误码。

### 5.6 带内联元素的句子

设置页有几句话夹着 `<code>`（`%s`、`gb`、`chrome://settings/searchEngines`）。**永远不用 `innerHTML`**（`ui.js` 现有约定）：文案里用占位符代表元素（`"网址模板中用 $CODE$ 代表关键词。…"`），`tNodes(key, [h("code", null, "%s")])` 先用私有区字符作标记格式化，再经 `splitMarked` 切开、把节点插回去。

### 5.7 go.html 不能等文案；首屏不闪

**go.html 的分屏路径不等 fetch：**

- `go.js` 一开始就发起 `const i18nReady = initI18n().catch(log)`，不 `await`，与 `main()` 并行。
- `main()` 的正常路径（解析、`loadConfig`、分屏、`location.replace`）和“读取配置失败 → `location.replace(兜底网址)`”路径都不碰 `i18nReady`。
- 只有写界面的函数等它：`setStatus`、`showError`、`offerLeftOnly`、防重入的“重新执行”按钮改成 `async`，先 `await i18nReady` 再写文字。这些只出现在出错、`leaveTab` 返回 `kept`、后退/刷新回来这几种情况，多等几毫秒没有影响。

**首屏不闪：**

- go.html：静态 HTML 里的文字清空，改用 `data-i18n`；`<html class="i18n-pending">` 加一条 `.i18n-pending main { visibility: hidden }`，`applyI18n()` 去掉这个类。正常跳转时用户看到的是一闪而过的空白背景，不会先出中文再变成别的语言。现在页面上那句“正在打开分屏…”也要等文案加载完才出现。
- 设置页：`<body class="loading">` 已经在渲染完成前隐藏内容。首次渲染时 `initI18n()` 与 `loadRaw()` 并行，两者都完成后 `applyI18n()`、渲染，再去掉 `loading`。

**字体**：go.html 写死了 `"Microsoft YaHei UI", "PingFang SC"`（简体字形）。改为按 `:lang()` 选：`:lang(zh-TW)` 用 `"Microsoft JhengHei UI", "PingFang TC"`。`<html lang>` 由 `setLocale` 设对后，`system-ui` 也会挑对字形。设置页同理。

## 6. 不做 RTL

首期 4 种语言都从左往右书写，不做 RTL。将来加入阿拉伯语等 RTL 语言时再单独设计（逻辑属性、`dir`、混排隔离、分屏“左/右”的说法）。新写 CSS 仍建议用逻辑属性，但不作为本期任务。

## 7. 不翻译的内容

- 产品名 `Split Search`；预置引擎名和用户自定义的引擎名。
- 网址、网址模板、`%s`、`_ss`、引擎 id、`chrome://settings/searchEngines`。
- 开发日志（`console.error("[split-search] …")`）；`scripts/e2e/**` 的向导页和报告（开发工具，继续用中文）。
- **要翻译**的示例值：对话框占位提示（`例如 baidu`、`https://www.baidu.com/s?wd=%s`）、引导里的 `gb`、“kg 关键词”。每种语言给一个当地常用、满足“可作左侧”规则的例子，作为单独的 key。

## 8. 与语言相关的格式

- 数字只有常量（id 1–20 个字符、名称最多 40 个字符），走占位符，用 ASCII 数字。
- 没有随运行时数量变化的句子，不需要 `Intl.PluralRules`。以后加入“共 N 个引擎”这类句子时按 CLDR 复数规则拆 key。
- 界面上没有日期；引擎顺序由用户决定，不按字母排序。
- 西班牙语一般比英文长 20%～30%，按钮和标签要能换行，9.3 的冒烟截图覆盖这一点。
- 页内语言和 Chrome 界面语言不一致时（例如选了西班牙语、Chrome 是中文），引导里的 Chrome 菜单名按所选语言写，和用户眼前的 Chrome 对不上。不处理：默认是跟随浏览器，主动改语言的用户能理解。

## 9. 测试策略

### 9.1 纯 node 测试

- **`test/i18n.test.js`**（测 `src/lib/i18n.js`）：`resolveLocale` 的映射表（`zh-CN`、`zh-TW`、`zh-HK`、`zh-MO`、`zh-SG`、`zh`、`en-GB`、`es-419`、`fr` → `en`，以及指定语言优先于浏览器语言）；`normalizeLocalePref` 对非法值返回 `"auto"`；`formatMessage` 的具名占位符（大小写不敏感、调换语序、重复使用）、直接 `$1`、缺参数给空串、`$$`；`splitMarked`。
- **`test/i18n-catalog.test.js`**：
  - `src/_locales/` 下恰好是 `en`、`zh_CN`、`zh_TW`、`es`，都在 CWS 支持列表里，`default_locale` 对应目录存在。
  - 4 份文件 key 集合完全相同；同一 key 在各语言声明的占位符名称集合相同；文案里的 `$NAME$` 都已声明、声明的都被用到；没有空文案；key 只含 `[a-z0-9_]`。
  - manifest 里每个 `__MSG_x__` 都存在；每种语言的 `ext_description` ≤ 132 个字符。
  - 静态扫描 `data-i18n` / `data-i18n-attr` 和 `t("…")` / `tNodes("…")` 的字面量 key 都存在；反过来，没被引用的 key 报错（错误码按 `ERROR_CODES` 计入引用）。
  - 守门：`src/` 下除 `_locales` 外的 `.js` / `.html` 不得出现汉字（注释除外）；`fetch(` 只允许出现在 `src/chrome/i18n.js`，且参数是 `chrome.runtime.getURL(...)`。
- **`engines.test.js`** 增加：`mergeConfig` 透传合法 `uiLocale`，缺省或非法值给 `"auto"`，不影响引擎合并结果。

### 9.2 现有单元测试

断言中文句子的地方改为断言错误码：`trigger.test.js`（5 处）、`options-edits.test.js`（6 处）、`engines.test.js`（1 处）、`config-store.test.js`（3 处）、`options-ui.test.js`（3 处）、`manifest.test.js`（`default_title`）。测试名和测试数据里的中文（引擎名“百度”）不是界面文字，不改。

### 9.3 e2e

e2e 有不少按中文文字判定的地方（`optpage.mjs` 的 `btn(row, "授权")`，`options-b*.mjs` 找“没授权”“已复制”“网站搜索”，`flow.mjs` 检查 go.html 的出错文字），测试浏览器的界面语言又不固定。处理：

1. **锁定语言**：准备阶段把 `uiLocale` 写成 `"zh_CN"`。e2e 本来就在运行前快照、结束后恢复 `storage.sync`，不影响用户数据，也不用改 Chrome 启动参数。
2. **按 key 找元素**：`h()` 生成的按钮带 `data-i18n`，`btn(row, "授权")` 改为 `row.querySelector('[data-i18n="engine_grant"]')`。
3. **期望文字从目录算**：node 端读 `src/_locales/zh_CN/messages.json`，用 `src/lib/i18n.js` 的 `formatMessage` 算出期望文字再比较，测试脚本里不再写中文字面量。
4. **新增 I18N 冒烟步骤（auto，可无头）**：在现有测试配置里依次把 `uiLocale` 设为 4 种语言，打开设置页和 go.html 出错页，检查 `<html lang>` 正确、没有 `missing message` 错误、没有元素文字等于 key 本身、没有横向溢出，每种语言截一张图存进报告目录（供人工检查和商店截图）。另外两项：在设置页下拉框里切换语言，页面不刷新就更新，随后打开的 go.html 跟着变；`uiLocale="auto"` 时，对每个 key 比较 `t()` 与 `chrome.i18n.getMessage()` 的结果，确认加载器的替换规则和 Chrome 一致。

页内切换让冒烟不再需要按语言启动临时配置，原先的 spike S3（临时配置 `loadUnpacked`）取消。manifest 级文案在别的语言下的显示不进 e2e，由 catalog 测试保证 key 存在，再靠 9.4 的 Windows 冒烟看英文。

### 9.4 Windows 冒烟

`docs/acceptance-v0.1.md` 第 2 节加两项：① Chrome 切到英文界面后，设置页（跟随浏览器）、go.html、工具栏按钮标题都是英文；② Chrome 保持中文、设置页选西班牙语，设置页和 go.html 出错页变成西班牙语，按钮标题仍是中文（符合 5.1 的限制）。

## 10. 文案润色与翻译流程

顺序固定：**先定中文源文案，再翻译**，源文案每改一次 4 种语言都要跟着改。

1. **抽取**（机械操作，不改措辞）：现有中文原样搬进 `zh_CN/messages.json`，同时完成第 5 节的代码改造。中文界面和现在完全一样，跑一遍完整 e2e 验证。
2. **润色中文源文案**（用户待办，2026-10-24 已记录）：对整个 `zh_CN/messages.json` 用 humanizer（中文用 humanizer-zh）和 lieflat-less-ai-tone 统一处理，用户确认后冻结。`docs/store/listing.zh-CN.md` 同批处理。
3. **术语表**（spike S4）：仿照 `scripts/e2e/steps/labels.mjs`，分别以 4 种语言启动 Chrome 155，从 `chrome://settings/searchEngines`、`chrome://extensions` 的 `loadTimeData` 读出 Chrome 自己的界面文字（搜索引擎、网站搜索、设为默认、开发者模式、网站访问权限、分屏等）。引导里提到的 Chrome 菜单名必须与对应语言的 Chrome 界面一字不差。
4. **英文**：用 content-l10n skill 从中文翻译，附术语表和每条 `description`；再用 humanizer 清理 AI 腔；用户审定。英文同时作为西班牙语的参照稿。
5. **繁体中文**：用 content-l10n 从简体本地化，不能只做字形转换（OpenCC 之类）。用词按台湾惯例（网址 → 網址、设置 → 設定、默认 → 預設、授权 → 授權），用户审定。
6. **西班牙语**：用 content-l10n 起草，中文为源、英文为参照，附术语表，再做一遍回译检查。有条件就请母语者看一眼，不阻塞上线，不进排期。
7. **以后改文案**：改 `zh_CN` 某条时，同一提交里更新其他 3 种语言。来不及翻译就先填英文，在 `description` 末尾标 `[needs-translation]`，catalog 测试只警告不报错，发版前清零。
